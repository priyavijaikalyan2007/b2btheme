# Dynamic UI

This brainstorm is about dynamic UIs. This is a new concept where the UI is not static. It changes depending on the context that user is working with. For example, if they are querying a table, then you have a SQL editor and a results viewer. If they are browsing schemas, you have a schema tree and a schema browser. If they are viewing reports, the report is assembled on the fly. This works best if the interaction is natural language and the rendering is dynamic.

I am anticipating such a future for knobby.io. To that extend we will need to think about how we discover compoennts, what is the right component, how to render them, how a visual canvas is assembled, state is persisted and restores, how the canvas history is stored with the conversation and more. Obviously, this is more of a power user capability becuase just a chat box does not lead to discoverability. So users will use a standard UI but over time as they get familiar with the product can switch to the dynamic UI.

Along with the dynamic UI, then there will be dynamic workspaces. I can create any number of workspaces depending on what I am working on. The entire history is preserved for each workspace and I can switch between workspaces for switching my work around.

## Dynamic UX Interactions

### Ideas

- #### Dynamic Workspaces

The dynamic workspace is the next core component but built on the chat hover and the dynamic canvas. A workspace is a collection of canvases. For example, imagine I am working on multiple projects as a T/PgM. I might want a separate workspace for each project. Within each workspace, I might have multiple different canvases. One showing project status, one showing action items, one showing decisions, one showing user feedback and so on. I can start a new canvas any time and I can pin / reorder canvases within a workspace. I can close canvases but I always have them in my history if I ever want to bring them back.

This sounds a lot like how Posthog's UI works but it's far more advanced and far more natural than that.

- #### Dynamic Canvas

The dynamic canvas is the heart of this UI concept. In essence, the canvas doesn't have a fixed screen or layout of components with some relationship to each other. Components are brought in dynamically as needed. For example, when I ask for a list of tables in a database, the table browser component (might just be a grid) is brought into the canvas. When I ask for the details for a specific table, the table metadata viewer (maybe just another grid) is brought onto the canvas. But, *crucially*, if I interact with the table browser and select a different table, the table metadata viewer updates to show metadata for the newly selected table. If I select two rows, then a new table metadata viewer component is brought onto the canvas to show both of them. This is a fundamentally different interaction model. There is an intelligent underlying system that asynchronously understands interactions based on the events generated by any component, ties them to the current state of the canvas and knows what to update, what to bring in, what to remove and how to udpate them.

- #### Chat Hover

The chat hover is another core aspect of the dynamic UI model. Chat is the primary natural language interaction surface. But, unlike present day models where the chat window is a right side or left side pinned sidebar, in our case, the chat surface is at the bottom and hovers over the canvas. The canvas slides behind the chat window at all times. A button summons a chat history windows overlay on the right sidebar. Clicking the history at any time should switch the canvas to that state in the time linked to whatever was being done there. At some later point in time, users may want to branch the conversation from any history. This will start a new canvas or a new workspace depending on their choice. This is similar to how Google is implementing Gemini in their latest Slides and Docs products.

## Implementation Nuances

### Ideas

- #### Component Mapping

A dynamic UI like we are aiming for requires components themselves to be very smart. We may need a layer above the raw UI component itself. For example, what does it mean to say "table viewer". Is that just a data grid? Or are we talking about a simple list showing table metadata? Or is it a more complex view showing composed of other components?

Microsoft recently published a LLM oriented charting language named Flint that aims to make it standardized and easy for LLMs to understand and visualize data. Likewise, Google published A2UI which is standardized UI described in JSON and rendered by the receiving agent according to its wishes. Like I mentioend before Posthog has a desktop style dynamic interface.

- #### Component Metadata

We would have to think about how suitability of a raw UI component for a particular purpose is expressed. Is that up to the consuming apps? For example, knobby.io uses components from the CDN to which the UI team publishes the open source enterprise grade components. We can include such suitability metadata directly in there for other apps to use or the metadata can live with an app. For example, is "database table browsing" better implemented using the "explorer" component or a "grid" component? What about situations where the data is complex enough to warrant further composition? For example, a collapsible panel with a grid or form within it?

I think this points to a potential DSL that is shipped with the components that describes how this works and how the canvas then renders components?

- #### CRUD

What about CRUD operations? What if a user wanted to delete a resource? Is a dynamic UI a read-only surface or a read-write surface? What actions are supposed? How do we express all that?

- #### RBAC

A further question is what happens when RBAC prevents the user from viewing, accessing or manipulating some content. What happens then? How does the canvas or component behave? My expectation is that the backend would filter our non-viewable assets. But what about actions? I suppose the best approach is to let the action through and the backend fail with a proper message instead? That may be frustrating the user; so we may need to hint at whether something is RO or RW for the user or the level of access as a hint. We need to think about this?

- #### Event Wiring

What about event wiring? How is the selection in a tree wired to what is displayed in a grid that is displayed on the same canvas? What if this needs to be broadcast across multiple canvas components? Is that then the job of the canvas to listen to all gnerated events and deliver events to all components and let them decide what to do? How does this happen dynamically? Does the canvas then implement a canvas wide, cross-component message pump similar to how Windows does it?

## State Preservation

### Ideas

- #### Canvas State

Preserving canvas state and snapshotting it each time is going to be important. The snapshot has to be linked to the conversation so that when a previous state in the conversation is selected, the canvas reflects the state as of that conversation. This means, each turn in the conversation itself is preserved as a unique entry and each canvas state is preserved as an entry and the two linked together in a many : one relationship. That is, multiple turn IDs can link to the same canvas Id becaue the canvas didn't change; or every turn Id might link to a separate canvas Id becuase it did change.

It will also be important to presever the "values" (but likely we will want whatever entity was used to fill the component) of the components in the canvas. This doesn't mean we should freeze the values but probably track whatever led to the component being loaded with that data.

- #### Workspace State

Similar to canvas state, we will want to preserve workspace state and snapshot it each time it changes.  Of course, with the chat hover preserving conversation turns and linking to the canvas Ids, the workspace state may be reduced to just preserving the canvases themselves, order, favorites, pins etc. But still, it is important to think about what needs preserving on the workspace.

Note that when we think about preserving state, we are preserving it for the user; that is, this has to be preserved on the backend. When the user switches to the dynamic UI mode, they see what they see when they left it last, even if they did that on another machine or browser or browser instance.

## Canvas Behaviors

### Ideas

- #### Canvas Positioning

Is positioning on the canvas absolute? I would think that is the best mechanism because auto-sizing and auto-placement is problematic. But it's a problem to solve.

- #### Component Bumping

Does resizing another component, bump another component? That is, when the rezise hits another component, do we stop when it bumps? How much tolerance do we give? Like do we give a defult 64px space? Is that even enough? What if the content needs scrolling? Do we put every component in a scrollable container too?

- #### Component Resizing

Do we allow component resizing? How would that work with other components surrounding the resized component? Do they also move, in turn moving everything else or is the resize a overlay? In that case, do we support each component being it ints own Z-index and incresing or decreasing in Z-index depending on what overlaps it?

- #### Infinite Canvas

It feels like a fixed canvas may not be enough. We may want an infinite canvas that has a top left origin and extends right and down. Of course, this leads to scroll issues and ever increasing context so we might need to think about when the canvas gets trimmed. When a particular piece of information is no longer relevant, we need to ruthlessly remove it so that the canvas never becomes overwhelming for the user.

- #### Canvas Panning

Obviously with an infinite canvas, panning and scrolling are going to be important.

- #### Canvas Clearing

If the user wants to, clearing the canvas is an option. Which brings up another question: are canvas manipulation commands such as "clear the canvas", "pan to data", etc. supported naturally or should we not support it and instead expose these actions as buttons?

- #### Editable Canvases

Is the canvas editable? Can I just remove an element that I don't want? What if I want to pin some information always? What about "always on" information such as sticky notes? Do we support support that on every canvas. Imagine this is a knowledge worker and they need to pin some notes about stuff so they can refer to that each time there they are working on a particular canvas. How do we make that happen? Almost like miro for example.

## Pinning

### Ideas

- #### Canvas Pinning

Users will likely want to pin some canvas states to a favorites. This is within the canvas itself and should bring up both the conversation turns and the canvas itself. This is useful for the user to go back in time when they want to.

- #### Workspace Pinning

Users will want to pin favorite workspaces. They may want to reorder favorites, name the favorites, remove from favorties etc. Apart from favorties, they may want to pin the status of a particular workspace at a particular point in time. This means that the workspace pin must include all canvas Ids so that the workspace can be restored back in time.

## Sharing

### Ideas

- #### Canvas Sharing

Is a canvas at a particular state shareable? Is the sharing always read-only? That is, I can share what I came up with you, but you can only view my canvas, never modify it. How do we pull that off? Inherently it feels like a canvas is a "personal workspace", not a "team workspace". But sometimes, it feels like brainstorm sessions are team workspaces, not personal workspaces. How do we even make this work? I do feel like any canvas can be shared RO or RW and if it is RW, then any user can update the canvas with the next turn; but that seems odd to me. It also feels visually and logically complex.

- #### Workspace Sharing

Similar to canvas sharing, workspace sharing seems intuitively important but also logically and visually complex. RO seems fairly straighforward but RW?

- #### Canvas Collaboration

Should we support commenting and comment threads on canvases and workspaces? Seems like this is easy to do and important if only RO sharing is implemented. At least this allows people to provide feedback and collaborate.
