# Agent Insights

Insights are hard-won lessons from real bugs, user feedback, and architectural decisions. Each insight captures a *principle* — not just what happened, but *why* it matters and *how* to apply it going forward.

**For agents**: Read this file at session start. When you discover a new insight during implementation, append it to the appropriate section with the date and a concise description. If no section fits, add a new one.

---

## 1. Cross-Repo & Cross-Team Contracts

### 1.1 Verify the Other Repo Before Planning "Their" Work (2026-07-11)
The Keycloak parity spec assigned R1 (theme-cookie write) to the apps team as outstanding work. Reading the apps repo directly (`~/work/knobby/apps`) showed `theme-manager.ts` had **already shipped** the cookie exactly per the R3 contract, and `apps/specs/infra/keycloak.prd.md` already documented the URL this repo was expected to publish. The plan changed from "draft an R1 patch" to "verify and hand off" — and revealed the theme repo was the actual blocker.

**Principle**: When a spec splits work across repos you can read, ground every "owned by the other team" claim in their code before planning. Specs go stale the moment either side ships.

### 1.2 Frozen Contracts Need an Executable Drift Guard (2026-07-11)
The AuthCard class structure is mirrored verbatim by Keycloak FreeMarker templates that live in another repo and deploy on a different cadence. Documentation alone cannot stop a well-meaning rename from silently breaking the mirror. The "canonical structure" test block in `authcard.test.ts` turns the contract into CI: any class/structure change fails the build here, before it breaks the login page there.

**Principle**: When markup or class names are consumed verbatim by an external system, encode the frozen surface as structure-assertion tests in the producing repo. A contract without a failing test is a hope.

### 1.3 Acceptance Criteria Can Exceed the Requirement Text (2026-07-11)
Spec R2 described theme-init as a synchronous pre-paint *set*, but acceptance criterion #3 ("toggling OS appearance while on the page updates it") silently requires a live `matchMedia` change listener. Implementing only the R-text would have passed review and failed acceptance.

**Principle**: Derive the implementation checklist from the acceptance criteria, not the requirement prose — and flag mismatches back to the spec owner so the text gets fixed.

## 2. CDN & Consumption Model

### 2.1 Pinning and No-Redeploy Are Opposing Goals — Pick Explicitly (2026-07-11)
Hard version pinning (or SRI hashes) maximizes tamper resistance but forces every consumer redeploy on every CDN release; SRI additionally bricks pages on any byte change. For same-organisation origins where the trust boundary is the Cloudflare account anyway, "latest + additive-only contract + CI drift guards" preserves evolution without redeploys (ADR-139, `CDN_CONTRACT.md`).

**Principle**: Choose a consumption model by asking *who must redeploy when this asset changes* and *what actually anchors trust*. Write the decision down; do not leave pinning policy implicit.

### 2.2 Cloudflare `_headers` Rules Accumulate — Keep Patterns Disjoint (2026-07-11)
Cloudflare static-asset `_headers` applies **every** matching rule, so overlapping patterns (`/icons/*` and `/icons/fonts/*`) emit duplicate `Cache-Control` headers with conflicting values.

**Principle**: Author `_headers` with mutually exclusive path patterns; comment the constraint in the file itself so the next rule addition doesn't reintroduce overlap.

## 3. Build Pipeline

### 3.1 Non-UI Scripts Can Ride the Component Pipeline (2026-07-11)
`theme-init.js` is not a UI component (no factory, no CSS, no stencil), but placing its source under `components/themeinit/` reused the entire tsc → export-strip → IIFE-wrap → terser pipeline and co-located vitest discovery (`components/**/*.test.ts`) for free; a one-line `cp` in `copy:js` published the canonical `/js/theme-init.js` URL. The exemption from UI-component conventions is documented in ADR-137.

**Principle**: Before building new pipeline machinery for an odd artifact, check whether the existing conveyor can carry it with a documented exemption. One copy step beats a parallel build path.

### 3.2 Generated Files Bite Manual Editors (2026-07-11)
`COMPONENT_INDEX.md` is regenerated by `npm run build` — hand edits are silently overwritten. Its description extractor also read the *continuation lines* of multi-line SPDX comment blocks in READMEs, leaking license text into descriptions (visible on `explorerpicker` long before this session).

**Principle**: Check a file's header for a generated-file banner before editing. When generated output looks wrong, fix the generator — the same defect is usually visible in older entries, and fixing it heals them all.

### 3.3 Count Assertions Are Change Detectors, Not Bugs (2026-07-11)
Adding the AuthCard stencil failed four diagramengine tests asserting exact shape-pack counts (111/138/150). That is those tests working as designed — forcing every stencil addition to be acknowledged.

**Principle**: When a count assertion fails after an intentional addition, update the expected count in the same commit as the addition, and say so in the commit message. Never widen the assertion to "greater than".

## 4. Security in a Component Library

### 4.1 Trusted-Markup Inputs Deserve a Named Boundary (2026-07-11)
AuthCard renders every option string via `textContent` — except provider icons, which are inherently markup (inline brand SVGs). Rather than accepting arbitrary HTML, the `iconSvg` option is (a) documented as app-authored-literals-only, (b) parsed with `DOMParser` and discarded unless the result is a single well-formed `<svg>` root, and (c) tested with an injection payload.

**Principle**: When a component must accept markup, isolate it to one named option, validate its shape as defense-in-depth, and state the trust requirement in the README — "trusted" is a documented contract, not an assumption.
