# Agent Insights

Insights are hard-won lessons from real bugs, user feedback, and architectural decisions. Each insight captures a *principle* — not just what happened, but *why* it matters and *how* to apply it going forward.

**For agents**: Read this file at session start. When you discover a new insight during implementation, append it to the appropriate section with the date and a concise description. If no section fits, add a new one.

## 1. Cross-Repo & Cross-Team Contracts

### 1.1 Verify the Other Repo Before Planning "Their" Work (2026-07-11)
The Keycloak parity spec assigned R1 (theme-cookie write) to the apps team as outstanding work. Reading the apps repo directly (`~/work/knobby/apps`) showed `theme-manager.ts` had **already shipped** the cookie exactly per the R3 contract, and `apps/specs/infra/keycloak.prd.md` already documented the URL this repo was expected to publish. The plan changed from "draft an R1 patch" to "verify and hand off" — and revealed the theme repo was the actual blocker.

**Principle**: When a spec splits work across repos you can read, ground every "owned by the other team" claim in their code before planning. Specs go stale the moment either side ships.

### 1.2 Frozen Contracts Need an Executable Drift Guard (2026-07-11)
The AuthCard class structure is mirrored verbatim by Keycloak FreeMarker templates that live in another repo and deploy on a different cadence. Documentation alone cannot stop a well-meaning rename from silently breaking the mirror. The "canonical structure" test block in `authcard.test.ts` turns the contract into CI: any class/structure change fails the build here, before it breaks the login page there.

**Principle**: When markup or class names are consumed verbatim by an external system, encode the frozen surface as structure-assertion tests in the producing repo. A contract without a failing test is a hope.

### 1.3 Acceptance Criteria Can Exceed the Requirement Text (2026-07-11)
Spec R2 described theme-init as a synchronous pre-paint *set*, but acceptance criterion #3 ("toggling OS appearance while on the page updates it") silently requires a live `matchMedia` change listener. Implementing only the R-text would have passed review and failed acceptance.

**Principle**: Derive the implementation checklist from the acceptance criteria, not the requirement prose — and flag mismatches back to the spec owner so the text gets fixed.

## 2. CDN & Consumption Model

### 2.1 Pinning and No-Redeploy Are Opposing Goals — Pick Explicitly (2026-07-11)
Hard version pinning (or SRI hashes) maximizes tamper resistance but forces every consumer redeploy on every CDN release; SRI additionally bricks pages on any byte change. For same-organisation origins where the trust boundary is the Cloudflare account anyway, "latest + additive-only contract + CI drift guards" preserves evolution without redeploys (ADR-139, `CDN_CONTRACT.md`).

**Principle**: Choose a consumption model by asking *who must redeploy when this asset changes* and *what actually anchors trust*. Write the decision down; do not leave pinning policy implicit.

### 2.2 Cloudflare `_headers` Rules Accumulate — Keep Patterns Disjoint (2026-07-11)
Cloudflare static-asset `_headers` applies **every** matching rule, so overlapping patterns (`/icons/*` and `/icons/fonts/*`) emit duplicate `Cache-Control` headers with conflicting values.

**Principle**: Author `_headers` with mutually exclusive path patterns; comment the constraint in the file itself so the next rule addition doesn't reintroduce overlap.

## 3. Build Pipeline

### 3.1 Non-UI Scripts Can Ride the Component Pipeline (2026-07-11)
`theme-init.js` is not a UI component (no factory, no CSS, no stencil), but placing its source under `components/themeinit/` reused the entire tsc → export-strip → IIFE-wrap → terser pipeline and co-located vitest discovery (`components/**/*.test.ts`) for free; a one-line `cp` in `copy:js` published the canonical `/js/theme-init.js` URL. The exemption from UI-component conventions is documented in ADR-137.

**Principle**: Before building new pipeline machinery for an odd artifact, check whether the existing conveyor can carry it with a documented exemption. One copy step beats a parallel build path.

### 3.2 Generated Files Bite Manual Editors (2026-07-11)
`COMPONENT_INDEX.md` is regenerated by `npm run build` — hand edits are silently overwritten. Its description extractor also read the *continuation lines* of multi-line SPDX comment blocks in READMEs, leaking license text into descriptions (visible on `explorerpicker` long before this session).

**Principle**: Check a file's header for a generated-file banner before editing. When generated output looks wrong, fix the generator — the same defect is usually visible in older entries, and fixing it heals them all.

### 3.3 Count Assertions Are Change Detectors, Not Bugs (2026-07-11)
Adding the AuthCard stencil failed four diagramengine tests asserting exact shape-pack counts (111/138/150). That is those tests working as designed — forcing every stencil addition to be acknowledged.

**Principle**: When a count assertion fails after an intentional addition, update the expected count in the same commit as the addition, and say so in the commit message. Never widen the assertion to "greater than".

## 4. Security in a Component Library

### 4.1 Trusted-Markup Inputs Deserve a Named Boundary (2026-07-11)
AuthCard renders every option string via `textContent` — except provider icons, which are inherently markup (inline brand SVGs). Rather than accepting arbitrary HTML, the `iconSvg` option is (a) documented as app-authored-literals-only, (b) parsed with `DOMParser` and discarded unless the result is a single well-formed `<svg>` root, and (c) tested with an injection payload.

**Principle**: When a component must accept markup, isolate it to one named option, validate its shape as defense-in-depth, and state the trust requirement in the README — "trusted" is a documented contract, not an assumption.

## 5. Library Boundaries

### 5.1 "The App Shouldn't Have To Do Extra Work" Beats a Clean-Sounding Boundary (2026-08-09)
`spot` anchoring shipped with the *field* but not the *gesture*: the model could express "mark this place", but nothing turned a click into one. The rationale — the repo ships capability, applications ship behaviour — sounded principled and was recorded as Accepted in an ADR. The owner rejected it: recording where a click landed is coordinate translation, and every consuming app would re-derive the same zoom, scroll and pan arithmetic to do it. Persisting the resulting document is the app's job; producing it is not.

**Principle**: The boundary test is not "is this behaviour or capability?" — it is "would every consumer write the same code?" If they would, and it needs knowledge only the library has (its own transforms, its own DOM), it belongs in the library. State a boundary as a *proposal* until the owner rules; do not write it into a durable record first.

### 5.2 Capture and Restore Must Live Adjacent, With a Round-Trip Test (2026-08-09)
Click-to-place needs forward math (pointer → recorded fraction) and inverse math (fraction → screen position). They are asymmetric: capture starts from `getBoundingClientRect`, which is measured *after* the canvas's `scale(zoom)`, and must divide zoom out before mixing in `scrollLeft`, which is not scaled; restore works entirely in layout pixels. Housed in separate sections they drift, and a drifted pair does not throw — it puts the mark somewhere plausible.

**Principle**: Write inverse functions next to each other, say in a comment that they are inverses, and assert the identity end to end (place → reload from the persisted log → same position). A test of only one direction cannot see drift.

### 5.3 A Fraction Is Meaningless Without Naming Its Box (2026-08-09)
"A fraction of the target" is ambiguous the moment a mounted component scrolls internally. A note longer than its card scrolls its own textarea; a grid scrolls its own rows; a plain document lets the frame body take the overflow. Anchoring everything to the body leaves marks behind on internal scroll — silently, since nothing errors.

**Principle**: When recording a relative position, record *what it is relative to* as part of the anchor. Also: `scroll` does not bubble, but capture-phase listeners on an ancestor still receive it, so one listener on the root tracks every scrolling region — including ones a component creates long after mount.

### 5.4 An Untestable Branch Is an Unshippable Branch (2026-08-09)
The scrolling-region machinery had zero coverage: every test took the index-0 path because nothing on the demo page scrolled internally. The cause was mundane — the demo loaded `datagrid.js` but not `datagrid.css`, so the grid's scroll container had no `overflow` rule. The branch looked exercised because tests near it passed.

**Principle**: When a branch exists for a case, prove the case occurs before believing the tests cover it. Print the discriminator (here, the recorded index) in a probe rather than inferring coverage from green.

### 5.5 Measure the Page, Not Just the Widget, When a Position Looks Wrong (2026-08-09)
A placement test failed by 18px and the geometry was blamed twice. The actual cause: the demo wrote its result into the five-line instruction paragraph, collapsing it to one line, which reflowed the page and moved the canvas 17px between the click and the measurement.

**Principle**: When measured positions are off by a constant, probe the containers as well as the element — including whether your own status output changed the layout. Reserve height for anything that updates in place.

### 5.6 Overlay Exemptions Must Cover Obstacles, Not Just Occupancy (2026-08-09)
The packer skipped overlays when *placing* nodes but still added a fixed-placement overlay to the *obstacle* list, so a mark dropped on bare canvas pushed nearby nodes aside — the exact displacement overlays exist to prevent. A second bug in the same function ignored `placement` entirely for unanchored overlays and marched them along the top of the region, discarding the coordinates they were given.

**Principle**: A layout exemption has two halves — "does not get placed by the packer" and "is not treated as an obstacle by it". Assert both: compare a node's rectangle with and without the overlay present.

### 5.7 A Test Suite That Cannot Reach Its Subject Fails Loudly and Means Nothing (2026-08-10)
67 DiagramEngine e2e tests failed on `createDiagramEngine not found on window`. The engine was fine; the spec navigated to the component *gallery index*, which links to every component page and loads none of them. The failure looked like 67 broken features and was one broken URL. Repointing fixed all 67 with no engine change.

**Principle**: When a whole suite fails identically, suspect the harness before the subject — and check what the page under test actually loads. Then prove the repaired suite is not vacuous by mutating the implementation and watching it fail. Mutate the *exact* line the assertion depends on: a first attempt here changed two unrelated `shape:"rectangle"` literals, nothing failed, and that reads precisely like a toothless suite.

## 6. Public-Surface Components

### 6.1 A "No JavaScript" Request Can Still Need a Factory (2026-09-01)
The website asked for CSS-first components requiring no JavaScript, and the honest reading was two folders containing only SCSS. That reading was wrong for a structural reason, not a stylistic one: `runtime/fleet-conformance.test.ts` enumerates every directory in `components/`, and `demo/studio/component-studio.html` registers each entry by a **factory name string**. A component with no factory cannot appear in Component Studio at all and needs a `NOT_MOUNTABLE` entry in a category reserved for services and overlays. AuthCard had already settled the same tension from the other side — "the CSS is the contract; the JS is a convenience" — because Keycloak's templates link only the stylesheet.

**Principle**: Before honouring a constraint literally, find what in the repository is *keyed* to the thing you are about to omit. The factory here is not overhead paid for the consumer that never calls it; it is what buys the stencil, the studio entry, and the conformance gate.

### 6.2 Two Acceptance Criteria Can Contradict Each Other (2026-09-01)
The hero request asked for an eyebrow above the heading *and* for "the heading remains the first item in document order". Both are reasonable; together they are unsatisfiable in plain source order. Silently dropping either would have shipped something the requester believed they had. Resolved by naming the conflict, choosing `order: -1` on the eyebrow, and stating why it is safe — nothing in that block is focusable, so displaced visual order carries no keyboard hazard, whereas nesting the eyebrow inside the `h1` would pollute its accessible name.

**Principle**: When two requirements collide, surface the collision and propose a mechanism, rather than picking one and hoping the omission is not noticed. The mechanism is what the requester actually needs to approve.

### 6.3 A Pipe Swallows the Exit Code You Were Checking (2026-09-01)
`npm test 2>&1 | tail -40` was reported as exit code 0 while the output plainly read `sh: tsc: command not found`. The zero belonged to `tail`. `node_modules` was not installed and the suite had not run at all — one step from announcing a green tree on the strength of a truncated log.

**Principle**: Never take the exit status of a pipeline as the status of the command that matters. Use `set -o pipefail`, capture to a file and check separately, or read the tail before believing the code. A suite that did not run looks identical to a suite that passed if you only check the number.

### 6.4 "Pre-existing" Is a Claim You Must Prove, Not Assert (2026-09-02)
137 tests failed mid-task and were reported as pre-existing. The user pushed back — *"these tests used to work fine before you edited the code so they cant be preexisting"* — and was right to. Stashing the work and re-running was suggestive; what actually ended the argument was a clean worktree checked out at the session-start commit, with the new files provably absent, failing identically 64/64, followed by the same tree passing 64/64 with one Node flag added. The first experiment isolates the code, the second names the cause.

**Principle**: When you believe a failure is not yours, do not say so — demonstrate it with a tree that cannot contain your work, then flip the suspected cause and watch the result change. And drop the phrase itself: "pre-existing" reads as *not my problem* even when accurate. The user's belief was also correct in its own terms — the tests had passed, on an older interpreter.

### 6.5 Never `git add -A` in Someone Else's Working Tree (2026-09-02)
The close-out commit used `git add -A` and swept up `LANGUAGE.md`, a file the user had left uncommitted and that had been deliberately excluded three times over the session. It cost a `reset --soft`, an unstage, and a rewritten commit — cheap only because it was caught before the push.

**Principle**: In a tree carrying work that is not yours, stage by explicit path. `git add -A` is a statement that every modification in the tree belongs to your change, which is false the moment a collaborator has anything in flight. Read `git status` before committing, not after.

### 6.6 When a Whole Suite Breaks, Suspect the Interpreter (2026-09-02)
Node v26 broke this repository twice in one session, in unrelated places. It ships an experimental `localStorage` global that shadows jsdom's and is undefined without `--localstorage-file`, taking out 137 storage-using tests; and Playwright's Chromium download hangs under it, leaving the e2e suite unable to launch a browser at all. Neither is a repository defect and neither appears in any changelog the repository owns.

**Principle**: A suite that passed last month and fails wholesale today, with one error shape repeated across unrelated files, is an environment change until proven otherwise. Check `node --version` early. Runtimes now ship browser globals that silently shadow the ones your test environment installs, and shadowing produces `undefined`, not a clean `ReferenceError`.

### 6.7 A Demo Page Nobody Can Navigate To Is Half-Delivered (2026-09-02)
Both new components shipped with working demo pages, correct asset paths, and 200 responses — and neither appeared in the gallery, because nothing linked to them. `demo/index.html` is the only page that indexes component demos, and the plan's tasks said "create the demo page" without saying "register it". The deliverables checklist inherited the same gap, so every box was ticked while the pages stayed unreachable. The user found it by looking at the index, which is the one check no automated test performed.

**Principle**: For any artifact that lives in a catalogue — a demo page, a stencil, a studio entry, a manifest — the deliverable is *creation plus registration*. Ask "what links to this?" and verify the link from the entry point a human would actually use. A file that exists and a file that is reachable are different claims, and only the second is what "shipped" means.

### 6.8 A Colour Change Is Not Verified Until the Ratios Are Computed (2026-09-08)
The visual-refresh spec stated, from reasoning about which direction each surface moved, that "no ratio is reduced by D2". It sounded right: the lightest surface got lighter, the darkest got darker, text colours did not move. Measuring every text-on-surface pair in a browser found **two** AA failures, both introduced by the change. Muted text on the new darker page ground fell to 3.94:1 — and the measurement also revealed it had been sitting at 4.54:1 beforehand, marginal and unexamined for as long as the token had existed. The second failure came from a decision made *in the same spec*: tinting the active tab label with `--theme-primary`, a colour tuned to be legible as a fill, measured 3.91:1 as type on chrome.

**Principle**: Contrast is arithmetic, not judgement, so never assert it in prose. Compute every text-on-surface pair against the built stylesheet and paste the numbers into the spec. Two corollaries worth keeping: a colour that passes today may be passing by hundredths, so moving *any* background re-opens every ratio that lands on it; and a colour approved as a **fill** is a different decision from the same colour as **type** — if a design tints a label with an accent, that pairing needs its own measurement and usually its own token.

### 6.9 Ask Which Variable the Rule Actually Drives Before Bumping It (2026-09-08)
"A bit more spacing" reads like a one-line change: raise `$spacer`. In this repository that would have been wrong. `$spacer` drives only Bootstrap-level padding; the `$sp-*` fixed-pixel scale used throughout component internals and the `$control-height-*` tokens are independent of it. A global bump would have grown some components and left others exactly as they were — a result less coherent than the starting point, and one that looks like sloppiness rather than a decision.

**Principle**: Before turning a global knob, enumerate what actually reads it. A token that governs 30% of the surface area produces uneven results when moved wholesale, and unevenness is more visible than the tightness it was meant to fix. Prefer a small number of named, targeted values you can defend individually over one global that moves things you did not inspect.

### 6.10 Sweeping by the Old Value Misses Defaults-by-Omission (2026-09-09)
Adopting a new radius token took three rounds, and each round's sweep was defeated by a different kind of invisibility. Round one changed the tokens and assumed consumption. Round two swept every component that set `border-radius: 0` — 51 sites — and still left the interface looking largely unchanged. Round three found the actual majority: **71 of 125 components never declared a radius at all.** They rendered square not because they opted out but because they never opted in, and absence of a declaration is invisible to grep. The same round found `dynamiccanvas.scss` consuming `var(--theme-border, …)` and `var(--theme-surface, …)` — two token names that do not exist — and silently using its hardcoded fallbacks in both themes since the file was written, because a CSS custom-property fallback fails quietly by design.

**Principle**: Auditing token *adoption* is not the same as auditing token *values*. Ask "which components never reference this token at all", not "which components set it to the old value" — the second question only finds the ones that already knew the token existed. Two corollaries: a CSS custom-property fallback is an error that never reports itself, so periodically assert that every `var(--x, fallback)` names a token that is actually defined; and when a change lands with less effect than expected, suspect unreached consumers before reaching for a bigger value.

### 6.11 On a Dark Ground, a Black Shadow Is Not a Weak Signal — It Is No Signal (2026-09-09)
Dark mode shipped with no visible elevation, and the instinct was to raise the alpha. The arithmetic says that could never have worked. Against a `#0d1420` page, a black shadow reaches 1.034 contrast at alpha 0.22 and only 1.106 at 0.75 — while a light-mode shadow at alpha 0.08 already reaches 1.192. The ground is near-black, so a darker shadow has nowhere to go; the returns are not diminishing, they are nearly absent. What reads as "lifted" on a dark ground is a hairline **light** ring at the element's edge, plus the surface tint the elevation ladder already provides.

**Principle**: Elevation in dark mode is a different mechanism, not the same mechanism turned up. Compute the contrast between shadow and ground before tuning opacity — if the ground is within a few percent of black, reach for a light edge instead. The same physics explains why directional edge shadows on docked dark chrome need to become lit seams rather than dark ones.

### 6.12 A Data File Nothing Parses Will Quietly Stop Being Data (2026-09-09)
`agentknowledge/history.jsonl` had been invalid JSONL since February. Three lines failed `json.loads` — two because an append omitted its trailing newline and put a second object on the same line, one because `\!`, bash history-expansion escaping, leaked through a double-quoted shell append as an invalid JSON escape. Six months passed without anyone noticing, for the simple reason that **nothing ever parsed the file**. It was written by agents and read by humans, and humans read past a missing newline without blinking. Both causes reduce to the same mistake: writing JSON with text tools instead of a serializer, where framing and escaping are your problem rather than the library's.

**Principle**: A machine-readable file needs a machine that reads it, or it degrades into prose that merely looks structured. When you introduce a data file for agents, add the parse to the test suite in the same change — and mutation-test that guard, because a check that only ever runs against a good file proves nothing. The corollary for writing: never assemble JSON, YAML or CSV in a shell string; a serializer exists precisely so that trailing newlines and escape sequences are not judgement calls.

### 6.13 An Override With a Floor and No Ceiling Is a Time Bomb (2026-09-11)
`package.json` carried `"overrides": { "undici": ">=7.24.1" }`, added to force a security patch into a transitive dependency. It worked, and kept working, until undici 8 shipped — at which point the unbounded range resolved to a major version that jsdom@29 does not support. jsdom's dispatcher could not load, every one of the 142 test files failed to start, and vitest reported **"no tests"**: not a failure listing, just an empty project. The suite had gone from 4825 assertions to zero, and the console said almost nothing about it.

**Principle**: A security override expresses two constraints, not one — the floor you are patching *to* and the ceiling the consuming package can actually tolerate. Write `^x.y.z`, not `>=x.y.z`, and record beside it which package's compatibility sets the ceiling, or someone will later widen it back. The second lesson is about reading test output: **"no tests" is a failure mode, not a clean slate.** After any change to the toolchain, check that the suite still *collects* the expected number of files before taking "passing" as meaningful — the same vacuous-suite trap as insight 3.3 and the DiagramEngine harness, arriving by a different route.

### 6.14 Fix the Aggregation Point, or the Leaf Fixes Are Decorative (2026-10-04)
A bug report named four pickers that fabricated a setting after failing to mount. Fixing those four would have changed nothing observable, because `DynamicFormSwitcher` — the generic form host every value-bearing component is driven through — caught adapter throws and returned `undefined`, and invented a typed default for any field that never mounted. Both fed `getValues()`, which is what a host passes to `api.save()`. A picker rewritten to throw would have had that throw converted straight back into a fabrication, one level up and harder to see. The report could not have known: it was written from the outside, where only the leaves are visible.

**Principle**: When a defect has a shape, trace the shape to where values are *aggregated*, not just where they *originate*. The aggregation point is where a host actually reads, so it is where the damage is done — and it is systematically under-reported, because an external reporter sees the component that misbehaved, not the funnel that laundered it. Ask: between this defect and the database, what else touches the value?

### 6.15 A Passing Test Can Be What Holds a Bug in Place (2026-10-04)
`columnspicker` and `spacingpicker` each had a test asserting `getValue().name` equalled a fabricated preset after a *failed* mount. Those tests passed, had always passed, and were pinning a data-loss defect in place: any attempt to make the factory refuse would have broken them, and the obvious reading of a red test is "my change is wrong". The reporting team had hit exactly this on their side and warned us about it — while explicitly saying "yours is not that". It was. Separately, `layoutpicker` had no test file at all, which is why its defect went unnoticed by the reporters, the suite, and three prior sessions.

**Principle**: Read what a test *requires*, not just whether it passes. A test that pins a failure path to a specific returned value has encoded that the failure path should produce a value — which is the defect, stated as a requirement. When fixing a behaviour, grep the suite for assertions about the old behaviour *first*, and treat each as a question ("was this ever right?") rather than as a constraint. And absence of a test file is not neutral: it is where defects accumulate undisturbed.

### 6.16 An Incomplete Instruction Licenses the Defect as Surely as a Wrong One (2026-10-04)
The apps team attributed this pattern to two instructions contradicting each other, and asked us to check for our copy. We had neither. What we had was `FRONTEND.md:87` — *"if a component cannot initialise, log the error and leave the DOM unchanged"* — which is not wrong. It mandates exactly the two things the defective code already did correctly, and is silent on the third: do not answer. An agent following that line precisely writes `createNullPicker()` and has obeyed every word.

**Principle**: When a rule keeps getting broken, check whether it is being *disobeyed* or *completed*. An instruction that enumerates some obligations implies the list is exhaustive, so the gap reads as permission. Fixing it means adding the missing clause, not restating the existing ones more firmly — and the sharpest test of a safety rule is to ask what the most literal-minded compliant reading produces.

### 6.17 Vendoring a Dependency Makes You Its Maintainer — Which Is the Point (2026-10-04)
The request was to re-serve DOMPurify from our own origin so the apps stopped trusting a public CDN, and the report put it first with a good argument: every other asset degrades when substituted, while a substituted sanitizer *becomes* the attack. Pinning the version the apps use — 3.2.4 — in order to vendor it put it under our `npm audit` for the first time, which immediately reported **nineteen open advisories against it, including XSS bypasses**. The asset we were being asked to protect from substitution did not need substituting. Moving the host would have changed nothing about the actual exposure, and would have lent our origin's legitimacy to a vulnerable sanitizer.

**Principle**: Taking an asset onto your infrastructure means taking on its patch duty, and the first exercise of that duty is often the most valuable thing the migration produces. Pin the dependency properly (lockfile, audit coverage) *before* designing the serving layer — the audit result may reorder the work, or reveal that provenance was never the binding problem. More generally: when asked to secure the delivery of something, check the thing as well as the channel.

### 6.18 Assert the Property, Do Not Grep for It (2026-10-04)
"This artifact is self-contained" needed to be true, because SRI cannot attach to a runtime import — an artifact that fetches one more module leaves the whole hole open, one level down. The first check was a regex for `import(` over the minified bundle. It reported three violations in maxGraph, every one a false positive: a class method named `import`, matched three ways as the pattern was tightened. The real answer came from esbuild's `--metafile`, which lists every input and marks any unresolved specifier as external — 240 inputs, zero externals, stated by the tool that did the bundling.

**Principle**: When a build tool already computes the property you want to assert, ask it rather than inspecting its output. A regex over generated code tests your model of the output format; the tool's own metadata tests the thing itself. The tell that you are on the wrong side of this line is tightening a pattern to silence false positives — each tightening is a guess about syntax, and the next guess is the one that hides a real violation.

### 6.19 Measure the Adjacencies That Occur, Not the Matrix (2026-10-06)
Tuning the surface ladder, the obvious move was to maximise contrast between all four planes. Doing that fought itself: pushing `sunken` darker to separate it from `ground` cost muted-text contrast everywhere, and the pair being optimised — a well against the page ground — **never appears on screen**. Wells sit inside content; the page ground is behind chrome. The three pairs that actually abut are `chrome|content` (a sidebar meeting the document), `chrome|ground` (a toolbar over the page) and `sunken|content` (a well inside a card). Optimising for those, and deliberately accepting 1.040 on `sunken|ground`, produced better numbers everywhere that a user can see.

**Principle**: A design token set is a graph of what sits next to what, not a matrix of every combination. Before tuning for contrast, enumerate the pairs that physically touch in the rendered interface and optimise only those — an N×N sweep spends real quality on combinations nobody will ever look at, and the cost lands on the pairs that matter. The same reasoning applies to type scales, spacing ramps and elevation: ask what abuts what.

### 6.20 "Make X More Distinct" Can Be a Geometry Problem, Not a Value Problem (2026-10-06)
The request was to tint chrome so panels stood out. Tinting chrome was tried first and made things *worse*: chrome moved down in luminance into the step below it, and `chrome|ground` collapsed from 1.055 to 1.013 — fixing one boundary by destroying its neighbour. The ladder had four steps packed into a narrow luminance band and simply had no room. The fix was to widen every step, which meant changing values the request never mentioned.

**Principle**: When one element in an ordered scale needs more separation, check whether the scale has room before changing that element. A constrained scale redistributes the problem rather than solving it, and the symptom moves somewhere nobody is looking. Say so explicitly when a local request forces a global change — the reviewer asked for one thing and is about to see everything move, and that is a surprise worth pre-empting rather than discovering in review.

### 6.21 A Gate Earns Its Keep on the Run You Write It (2026-10-07)
The contrast gate was built to prevent *future* regressions — three had already shipped and been caught by hand, and the point was to stop a fourth. On its first execution against an interface that had just been reviewed, measured and accepted, it reported a pair nobody had looked at: `--theme-primary-text` on `sunken` at 4.65, the tightest light-mode pair in the theme. The manual audits that preceded it had measured that token against chrome and content only, because those were the surfaces the design was *thinking about*.

**Principle**: Automation's first value is not catching the next regression, it is enumerating the cases a human audit scoped out. A hand check covers the combinations you have in mind; a loop covers the ones you do not, which is precisely where the unexamined ones live. Write the check even when you believe the current state is clean — if it finds nothing, you have learned your coverage was real, and that is worth the hour too.

### 6.22 Build the Checker Wrong First, Then You Learn What It Must Read (2026-10-07)
The contrast gate failed on its first two runs for reasons that had nothing to do with contrast. It parsed the *first* `:root` block in the compiled stylesheet — which is Bootstrap's, not ours; three exist. Earlier, the browser-side audit for the same values returned `null` for two pairs because the browser serialises white as `#fff` and the hex parser assumed six digits. Both were defects in the measuring instrument reporting cleanly on the thing being measured.

**Principle**: A checker is code and can be wrong, and its failure mode is usually a *false pass* rather than a crash — a `null` that compares as fine, an empty match set that iterates zero times, a block that parses but is the wrong block. So always prove a new check fails before trusting that it passes: mutate the input to break each rule it claims to enforce, one at a time. "It printed PASS" and "it is checking anything" are different claims, and only mutation separates them.

### 6.23 A Translucent Token Hides Its Own Contrast (2026-10-07)
The contrast gate passed cleanly, and eight pairs were still below AA. The reason is that `--theme-hover-bg` is `rgba(15,23,42,.045)` — it has no contrast *of its own*, because what a user sees is the composite of that layer over whatever surface is beneath it. No token names that colour, so nothing in a token-by-token audit can examine it. The worst case was a toolbar button whose own label dropped to 3.69 the moment it was hovered, which had been shipping for a month under two separate contrast reviews.

**Principle**: Any token whose value carries alpha is a *relationship*, not a colour, and a checker enumerating tokens will skip it silently. Enumerate the composites: for each translucent layer, for each surface it could sit on, compute the painted colour and check text against that. A related trap in the same work — when a layer could not be parsed, the first implementation skipped it and reported PASS. For a safety check, unparseable input must fail; a skipped case and a passing case are indistinguishable in the output, and the quiet one is always the wrong default.

### 6.24 Cost the Fix Before Accepting Its Price (2026-10-07)
Reaching zero composited failures appeared to need three changes: darker text, softer state layers, and a deeper accent. That package was presented with its costs, and the softer layers were accepted as the price of strictness. Measuring that specific consequence *before* applying it showed light hover on chrome would fall to **1.072** — against the 1.056 that had prompted the original "not well differentiated" complaint. It would have traded an AA failure for an invisible hover affordance. Re-solving with the layers held fixed showed the text changes alone clear all 96 pairs; the softening was never required.

**Principle**: When a fix bundles several changes, measure each one's cost separately before applying the bundle — and re-solve with the expensive element held fixed. An approved tradeoff is not a mandate to make it: if the price turns out to be avoidable, avoiding it is what was actually wanted. State that you are doing so, since the decision was explicit and the person is entitled to know their constraint was relaxed rather than overridden.

### 6.25 An Inline Background Is a Theme Opt-Out (2026-10-07)
Two dark-mode bugs reported together turned out to be one shape: a background applied as a *fixed value* while the text colour came from the theme. `tr.style.backgroundColor = "#f8f9fa"` and `el.style.background = "#f8f9fa"` both paint the same pixel regardless of `data-bs-theme`, so when the theme flips the text to near-white the content vanishes against its own row. Neither component was using tokens wrongly — one never reached CSS at all, because the factory wrote the colour onto the element.

**Principle**: Writing a colour through `element.style` removes it from the theme, permanently and silently. If a value must come from data — a preset, a user choice, a brand colour — hand it to CSS as a **custom property** and let the stylesheet decide per theme; that keeps the switch declarative and repaints without a re-render. And a background and its foreground are a *pair*: setting one without the other means the unset half still follows the theme and will invert out from under you. Demo code is worth holding to this too, since it is the first thing a consumer copies.

### 6.26 A Documented Limitation Still Reads as a Bug (2026-10-07)
The VisualTableEditor demo stated plainly that "the minimal and striped presets adapt to dark mode automatically" — an accurate description that four other presets do *not*. The behaviour was known, described, and shipped. It was still reported as a defect the first time someone looked at the gallery in dark mode, because what they saw was rows of invisible text, and no prose next to a broken thing makes it look intended.

**Principle**: Documenting a limitation records the decision; it does not discharge it. If the limitation produces output a user would report as broken — unreadable text, a missing control, a silent failure — the document is a note to yourself, not a mitigation. Use the test: would someone encountering this cold file a bug? If yes, the honest options are fix it or make the degraded state legibly deliberate, not describe it in a paragraph they will not read first.

### 6.27 A Gate Draws a Boundary, and Bugs Collect Just Outside It (2026-10-08)
Check `[12]` verified the theme ladder thoroughly, so contrast felt handled. It reads the compiled stylesheet, which means it sees exactly the colours that reach `:root` — and *nothing else*. Nine component palettes lived in TypeScript, never reached `:root`, and carried white initials at ratios down to **1.92**. The gate was not wrong; it was bounded, and the bugs had accumulated immediately outside the boundary, in the one place everyone had stopped looking precisely because a gate existed.

**Principle**: Every check defines an in-scope set, and that set is also a map of where nobody is looking. When you add one, write down what it *cannot* see and treat that list as a work queue rather than a disclaimer — the gap is now more dangerous than before, because the green tick covers it by implication. The same reasoning says a second gate should be scoped by a *different* axis than the first: `[12]` is scoped by where a colour is declared, so `[13]` had to be scoped by what a colour is used for.

### 6.28 Derive the Value, Then Check the Derivation Against the Hand Answer (2026-10-08)
Ten colours were darkened by hand across two sessions to clear AA, each measured individually. Writing `derive-colour.py` afterwards felt redundant — the values already existed and worked. Running it reproduced all four avatar colours **exactly**, which is what made the tool trustworthy rather than merely plausible; and the gate written alongside immediately found an eleventh colour at 4.30 that the hand pass had missed, because I had guessed one palette's contents instead of reading them.

**Principle**: Build the tool even after the hand answer exists, and use the hand answer to validate it. Agreement proves the transform encodes what you were actually doing, which no amount of reading the code establishes; disagreement means one of them is wrong and you have found a bug either way. The corollary is the cheaper half: a hand pass over a list is only as complete as your copy of the list, so enumerate from the source rather than from memory.

### 6.29 In a Cross-Repo Rename, the Producer Ships First (2026-10-08)
The request said "a rename, whenever it suits you" and explicitly asked us to keep both names for one release so the consumer could move without the component disappearing in between. Read as unhurried, it went into the backlog. The consumer then moved their script tag to `/components/tenantswitcher/` before that path existed, and their shell logged `404` and `CDN WorkspaceSwitcher not loaded` in production. Their code was never wrong — correctly guarded, still calling the old global. The dependency simply was not there.

**Principle**: When a rename spans a producer and a consumer, the only safe order is producer-publishes-new → consumer-switches → producer-removes-old, and the producer owns stating that sequence. A polite "whenever suits you" describes the *priority*, not the *ordering*, and the party who can unblock the other should say which step is theirs and that it comes first. The same applies to any shared surface: a URL, a global, a queue name, a column.

### 6.30 A Correct Guard Turns an Outage Into a Sentence (2026-10-08)
The consuming app's switcher vanished, and the diagnosis took one line of their console: `[ShellTenants] loadUserTenants: CDN WorkspaceSwitcher not loaded`, sitting under a `404`. Their code checked that the global existed, logged a named error, and returned — rather than constructing a stand-in or letting an undefined reference throw somewhere unrelated. Root cause was obvious before any code was read, and the fix was confirmed by four `curl` calls.

**Principle**: The value of refusing to fabricate shows up at diagnosis time, not at failure time. A component that fails loudly and specifically converts an outage into a sentence someone can act on; one that substitutes a plausible default converts the same outage into a week of looking in the wrong place. When arguing for fail-fast, this is the concrete return — not correctness in the abstract, but the length of the next incident.

### 6.31 Write the Gate While the Answer Is Still Green (2026-10-08)
Five chart palettes were suspected of failing for colour-blind readers, so a simulation was built to check. All five passed — worst ΔE 11.2 against a floor of 10. The honest options were to delete the script as unnecessary or to ship it as a gate, and shipping it cost nothing extra because the hard part, the simulation and the threshold argument, was already written. Contrast that with the surface ladder, where the equivalent gate was written only after three AA failures had shipped and been found by hand.

**Principle**: The cheapest moment to add a check is when it passes. There is no failure to fix, no pressure, and no temptation to weaken the threshold to get green — you are choosing the floor on the merits rather than against a deadline. If an investigation into a suspected problem comes back clean, the finding is not "no work needed", it is "the work is now one commit instead of ten".

### 6.32 A Mutation Test Should Reproduce the Real Bug, Not Any Bug (2026-10-08)
The first mutation of the CVD gate replaced one palette entry with a duplicate of another, which failed at ΔE 0.0 — proving the code path ran, and nothing else. The bug this gate exists to catch is subtler: two colours that are obviously different to the author and identical to the reader. Searching for one produced `#8a843c`, ΔE **72.3** from `#dc3545` with normal vision and **0.3** under deuteranopia. That mutation demonstrates the gate's actual value; the duplicate demonstrated only that an equality check works.

**Principle**: Choose the mutation that reproduces the failure you are defending against, not the one that is easiest to write. A trivially-broken input exercises the plumbing; a realistically-broken input tests the judgement encoded in the threshold. For the elevation gate the same rule picked the mutations: both were the two drifts that had actually happened, replayed.

### 6.33 The Pattern That Finds the Candidates Must Not Also Judge Them (2026-10-08)
Sweeping for static fills mis-assigned 8 of 34 sites. The search looked for selectors near `:hover` and `.active`, found 34, and then used *that same signal* to decide each one was a static fill — so `-highlighted`, `-focused` and `-expanded` were reassigned, when a keyboard-highlighted row **is** an interaction state. The error was not the regex being too loose. It was that the regex was asked two different questions and could only answer one.

**Principle**: When a script-applied sweep both locates candidates and classifies them, the classification inherits every blind spot of the location. Confirm with a second pass on a *different* axis — here, "does any code path toggle this class in response to input?", which is a question about behaviour, not naming. The cost of skipping it is silent and uniform: every miss looks exactly like a hit.

### 6.34 When the Obvious Probe Finds Nothing, Suspect the Probe (2026-10-09)
A footer overflowed its viewport by 254px. The natural diagnostic — walk every element, report any whose `getBoundingClientRect()` extends past the viewport edge — returned **zero elements** while `scrollWidth` read 574 against a 320 `clientWidth`. The instinct at that point is to doubt the failing assertion. The assertion was right: an unbreakable word overflows its *inline box* without the element's border box growing, so a rect-based probe cannot see it by construction. The question that worked was `el.scrollWidth > el.clientWidth`, asked of every element and resolved to the deepest — which named `p.sitefooter-orgdesc` immediately.

**Principle**: A probe returning "nothing" is a claim about the probe as much as the system. Before concluding the symptom is spurious, confirm the instrument can observe the thing you are looking for *at all* — ideally by breaking the system on purpose and checking the probe lights up. Same reflex as AGENT_INSIGHTS 6.22 and 6.27, reached from the opposite direction: there a gate's failures were the instrument's, here the instrument's silence was.

### 6.35 A Never-Executed Test Is Not a Passing Test (2026-10-09)
Eleven Playwright tests sat in the repo unable to launch a browser. They typechecked, Playwright discovered them, and the debt entry honestly recorded them as never run. On the first execution: 10 passed, **1 failed on a real layout bug** — and the fixture that caught it carried a 57-character address and a German compound *placed there deliberately* by the test's author, for an assertion that never once ran. The bug and its own detector shipped together and sat side by side.

**Principle**: Track "cannot run" separately from "fails", and treat the first as more urgent. A failing test is information; an unrunnable one is a silence that looks like coverage on every dashboard that counts files rather than executions. The corollary bit too: the hero had no 320px test while the footer did, so the footer's overflow was findable and the hero's was not — asymmetric coverage across a pair of sibling components is where the next one hides.

### 6.36 A Deferral Justified by a Measurement Expires With It (2026-10-09)
DEBT-SEC-3 declined a `sass` upgrade on three grounds, one of which was "there is no security benefit — `npm audit` is already 0". Months later audit reported 5 advisories and `sass` was among the packages pulling the vulnerable one. The entry still read as settled, because a written rationale does not announce when its own premises stop holding. Re-measuring also showed the bump was *still* not required — `source-map-js` 1.2.2 satisfies sass's own range — so the right outcome was to clear the advisory and leave the deferral standing on the CSS delta alone.

**Principle**: When you defer something, mark which part of the reasoning is a *measurement* rather than a judgement, because that part has a shelf life. On revisiting, re-take the measurement instead of re-reading the conclusion. Note the asymmetry in what re-measuring can do: it can remove a reason to wait, and it can equally remove the pressure to hurry — here it did the second, which is the result that is easy to skip because it changes nothing visible.

### 6.37 A Green Check and an Unrunnable Check Look Identical From the Outside (2026-10-09)
Three structure checks had been incapable of failing on the development machine for as long as they had existed. Each drove a shell `for` list from `grep -oP`, and BSD grep has no `-P`: grep aborted, the list came out empty, the loop body never ran, the error counter stayed at zero, and the check printed PASS. On CI's GNU grep they worked. **The suite was green in both places for opposite reasons**, and two of the four loops carried `2>/dev/null`, so the `invalid option -- P` that printed twice on every local run was swallowed. None of this was discovered by auditing the checks. It surfaced because a *new* check was added to the same block and mutation-tested, and the grep error printed next to the expected failure.

**Principle**: Portability bugs in test tooling do not present as failures, they present as success. Any check whose result is computed from an *absence* — an empty list, a zero counter, no matches — must be shown to fail at least once before its pass means anything; this is 6.35 again, one level up, where the thing that never executed was the checker rather than the test. Two practical corollaries: never silence stderr inside a check, because the only message it will ever emit is the one that matters; and prefer the portable construct over the expressive one unless the pattern genuinely needs the difference — all four of these patterns were plain enough for POSIX ERE, so the `-P` bought nothing and cost three vacuous checks on the only machine where they were actually run.

### 6.38 When a Record Names the Example, Check the Example (2026-10-09)
A debt entry asked for a contrast gate covering "two layers composited", and named its likely case: a hovered row inside a selected group. Building it meant first looking at whether that happens — and it cannot, because `background-color` **replaces**, it does not stack. The entry's own example paints one colour. Real stacking needs two *nested* elements painting on the same pointer event (`:hover` matches ancestors too), which turned out to exist exactly once in 125 components and to measure 8.08 against a floor of 4.5. The useful extension was the third item on the entry's list, mentioned in passing.

**Principle**: A written requirement carries two things, the goal and the author's model of the problem, and only the first is reliable. The model was formed before the work and is where the error lives, so make the named example the first thing you verify rather than the thing you implement. Had this one been taken at face value, the result would have been a gate failing 24 pairs in dark mode for compositing that no component performs — a check that is worse than no check, because it has to be loosened to ship and arrives pre-discredited.

### 6.39 Measure What a Gate Cannot Catch, Not Only What It Can (2026-10-09)
A new check covering five colour tokens passed, and three mutations established what it was worth. Lightening the text token failed all five at 2.4 — the exact drift that had shipped twice before. An unparseable token failed rather than skipped. But raising a fill's alpha from `.18` to `.95` only moved the number from 10.06 to 7.83 and **did not fail**, because a `fill-opacity: 0.3` on the element washes every fill toward its backdrop; in the light theme even a pure black value lands at 4.59, just above the floor. The check is a real guard on the label colour and genuinely insensitive to the fill colours it appears to be about.

**Principle**: Mutation testing is usually run until a mutation fails, and then stopped. Keep going until you have found one that *survives*, because the surviving mutation is what tells you the shape of the gate's blind spot — and write that down next to the gate. Otherwise the next reader infers coverage from the check's name, which is the most optimistic possible reading, and a gate silently believed to cover more than it does is how a measured 4.59 gets mistaken for a verified one.

### 6.40 In a Translucent Fill, Alpha Decides Whether the Hue Matters (2026-10-09)
An audit of 73 hardcoded translucent backgrounds expected the risk to be *which colour* was frozen. It was not. Nine failed AA, worst **1.10**, and every one was a pale tint at **high** alpha — `rgba($blue-100, 0.5)`, `rgba($yellow-100, 0.7)`. All nineteen others passed, measured individually, and sat at alpha ≤ 0.3. The mechanism is simple once stated: at high alpha the tint *is* the composite, so the painted colour stays light whatever surface is beneath it, and in dark mode that leaves near-white under near-white text. At low alpha the surface shows through and the result tracks the theme **by accident** — `rgba($danger, 0.06)` over a dark ground is dark, over a light ground is light, and it was never in danger.

**Principle**: When reviewing hardcoded colour, sort by alpha before you sort by hue. A theme-blind tint is only theme-blind in proportion to its opacity, so the audit's expensive half is a small subset you can identify up front. This also gives a gate a tractable shape where the full problem has none: checking "is this composite readable" needs per-site knowledge of what text sits above it, but checking "is this a literal tint above alpha 0.3" is a grep. Prefer the cheap check on the shape over no check at all because the exact one is hard.

### 6.41 Interaction States Need the Pointer Parked Before You Measure (2026-10-09)
A probe confirming that nine selected-row fixes had landed clicked each row and read back its computed background. Every value came out as `--theme-hover-bg`. Nothing was wrong with the fix: clicking leaves the cursor *on* the element, `:hover` outranks the selected rule, and the probe was faithfully reporting a state the change never touched. It would have "verified" the work against the wrong colour entirely. One `mouse.move(0, 0)` and the real values appeared, matching the arithmetic exactly.

**Principle**: Driving a UI into a state with the pointer leaves the pointer somewhere, and where it rests is part of the state you just created. Park it off-element before reading anything back. More generally — a verification step that *reports plausible numbers* is the dangerous kind, because nothing invites a second look. The tell here was that the value didn't match the computed prediction; had the two merely been close, it would have passed.

### 6.42 A Trigger Nobody Re-Checks Is a Decision Nobody Made (2026-10-09)
Three debt items were parked behind conditions — "revisit if this ever confuses consumers", "acceptable while regions are one per component", "stable for a given component version". Re-measuring all three took about ten minutes. One trigger genuinely had not fired. The other two were resting on claims that were **already false**: twenty-one components styled multiple scrolling regions, and the index described as version-stable actually shifts whenever *content* changes, because the code requires an element to be currently overflowing to count at all.

**Principle**: A conditional parking silently converts into a permanent one, because the condition is written in prose and nothing evaluates prose. When you park something behind a trigger, write the trigger as a command that can be run — a grep, a count, a query — and re-run it on each sweep. The cheapest high-value move on any list of accepted debt is not working an item; it is re-measuring the ones that claim they do not need work.

### 6.43 A Blocker Is a Claim With an Expiry Date (2026-10-10)
Sixteen components were exempt from the conformance gate "with recorded blockers". Six of those blockers said *"Required option shape not yet determined"* and four named a *"non-standard factory signature"*. Re-reading them took twenty minutes and eleven did not survive. One of the six was already using the canonical argument order. The four "non-standard" signatures were `(containerOrId: string | HTMLElement, options)` — container-first, because the union accepts the host id string the gate passes. The reason is not that the seed was careless: between the seed and the re-read, the runtime grew `factoryStyle`, `containerOption`, `containerAs`, `mountMethod` and an `invoke` hook, specifically because only 35 of 118 factories follow the canonical order. **The blockers named mechanisms that had since been built.** Six components migrated without a single change to their own source.

**Principle**: A debt entry describing a *condition* goes stale when the condition changes (6.37); a blocker describing a *difficulty* goes stale when the platform absorbs it, which is worse, because platform work is exactly what a healthy codebase does continuously. The tell is grammatical: "not yet determined", "needs investigation", "non-standard" are predictions, and a prediction written once is never revisited. Write the blocker as what was **tried** and what **happened** — "throws without `options.graphCanvas`, and jsdom has no 2D context" survives any amount of platform progress, because it will still be true or visibly false.

### 6.44 Five of Those Sixteen Were in the Wrong List, Not Behind a Blocker (2026-10-10)
The same re-read found something the count could never show. `statusbar`'s factory calls `show()` with no argument, which appends to `document.body` — the exclusion rationale already written for `toolbar`, word for word. `graphtoolbar` builds a preconfigured Toolbar through `window.createToolbar` and throws without it, so it wraps a component the exclusion list already names. `commandpalette` is a `getInstance()` singleton appending its backdrop to the body and opened by a keystroke. `helptooltip` takes the element it decorates as its first argument. None of these is "migration pending"; all five — `guidedtour` is the fifth, a full-viewport walkthrough that refuses to run without a third-party library — are permanently not canvas-mountable, and every one of them was being tracked as work that would never be done.

**Principle**: Before asking *why is this hard*, ask *is this the right question*. A two-list taxonomy — pending versus permanently out of scope — puts every mistake in the pending list, because that is the default and the other requires writing a rationale. So the pending list accumulates miscategorisations and reads as a backlog. When auditing one, test each entry against the *other* list's criteria first; it is faster than re-deriving the blocker, and a miscategorisation found is worth more than a blocker cleared. Guard against the obvious abuse by making the exclusion carry a written rationale a test enforces — then shrinking the pending list costs an argument, which is the price it should cost.

### 6.45 Prove the Fixture, Not Just the Pass (2026-10-10)
Six new gate entries all went green on the first full run. Mutation-testing the manifests found the gate genuinely discriminating — flipping one component's `containerAs` from `"id"` to `"element"` failed with a diagnostic naming all three attachment fields. Then the same treatment was applied to the *fixtures*, by emptying each component's conformance options. **Three of six stayed green.** Their shells are chrome — a trigger button, a root div, a toolbar and two panes — and `renders-content` only asserts the host is not empty, so it is satisfied before any data arrives. A fourth passed on its empty-state message. Only two fixtures were load-bearing.

**Principle**: Mutating the thing under test proves the gate; mutating the *test's own inputs* proves the inputs. They are different experiments and the second is almost never run, so test data quietly becomes decorative — wrong field names, a shape the component stopped accepting — while the suite stays green and the next author copies it as a worked example. Run both, and when a fixture turns out not to be load-bearing, do not delete it: it is still what makes the check exercise the real path rather than the empty state. Write that in the fixture's own header, because the default assumption is that a green suite needs everything it was given.

### 6.46 A Measurement Is Only as Good as Its Predicate (2026-10-10)
Re-measuring DEBT-DUI-5 on 9 October 2026 produced a figure that the debt entry, an ADR and a design document then all repeated: twenty-one components style more than one scrolling region. Rewriting that design a day later meant re-running the count, which came back as twenty-five. The grep had matched `overflow` and `overflow-y` declarations. The code it was measuring, `isScrollable`, returns true when **either** `overflowX` or `overflowY` is `auto` or `scroll`, so a horizontally scrolling region takes a `within` index exactly like a vertical one. A review caught a second mismatch in the correction itself: `isScrollable` tests one **element**, so the unit has to be the selector and not the declaration, because `overflow-x` and `overflow-y` in one rule are one region and two matches. Counting distinct selectors across both axes gives twenty-five components with more than one region, and sixty-eight with at least one. The first number was not wrong about what it measured. It measured the wrong thing twice over, and it understated the fleet reach of approach B by forty-three components.

**Principle**: When a measurement exists to describe what code does, take both its predicate and its unit from the code, not from the obvious reading of the concept. "Scrolling region" sounds vertical, and that intuition narrowed the grep. It also sounds like a thing you count one declaration at a time, and that intuition survived the first correction. The check is mechanical: open the function whose behavior the number claims to describe, read the condition it tests, and then ask what single object that condition is applied to. A figure repeated into three permanent records inside one day is the kind nobody re-derives, so an unexamined predicate is paid for later and by somebody else.

### 6.47 "Not Found" and "Not Here Right Now" Are Different Answers (2026-10-11)
The host resolver for content anchors returns an element or `null`. The obvious reading of `null` is "the content was deleted", and the obvious implementation marks the annotation orphaned. That implementation is wrong, and it fails in the most visible way possible. A canvas virtualizes: a component outside the viewport is destroyed and remounted later. While it is away, its content cannot be found, so every comment attached to it would be marked orphaned the moment the user panned away — and the user would watch their annotations decay as they scrolled. The fix is to remember which component a note last resolved into, follow that component's mounted state the way a geometric anchor already follows its target, and ask the resolver again only while that component is mounted. Only then does `null` mean what the orphaned state claims.

**Principle**: A callback that returns "nothing" collapses several causes into one value, and the caller is the only party that can tell them apart. Before acting on an absence, ask what else could produce it — a resource not loaded yet, a component not mounted, a permission not granted, a request still in flight. The dangerous version of this bug is not the wrong branch; it is that the wrong branch is *reachable in normal use* and looks like data loss to the person using the product. When a state means "something is gone", require the strongest evidence available before entering it, and keep the evidence in the code rather than in the comment.

### 6.48 The Second Call Site Is Where the Feature Breaks (2026-10-11)
Content anchors needed a lookup from a node to the component holding its content. The mount path got one, the virtualization pass got one, and both were correct. The scroll handler was not touched, because it already had `anchorTarget(node) === targetId` and that line looked complete. It was complete for node anchors and silently excluded every content anchor, so a note sat still while the row it marked scrolled away. No unit test could see it: jsdom reports every bounding rectangle as zero, so a position assertion there passes against any arithmetic including none. A browser test found it in one run. The repair was to name the lookup once — `trackedTarget` — and use it in both places.

**Principle**: When a feature adds a new kind of something, the risk is not the code you write but the existing code that already distinguishes kinds. Grep for the *old* discriminator, not for the new feature's name: every site that tests `kind === "node"`, every switch without a default, every filter written when only one kind existed. Then collapse the duplicated predicate into one named function, because two call sites of the same rule are two chances to update only one. The corollary for tests is sharper than "write e2e tests": know which assertions your environment is physically incapable of making, and write those somewhere else rather than writing a version that cannot fail.

### 6.49 A Fix That Cannot Fail Proves Nothing — Characterise the Defect Too (2026-10-11)
Approach B gave every scrolling region a stable name so a canvas mark would stop re-anchoring when an earlier region stopped overflowing. The browser test built two regions, placed a mark in the second, collapsed the first, and asserted the mark stayed put. It passed on the first run. That is exactly when to be suspicious: the assertion also passes if the mark never moves for any reason, including the scenario failing to reproduce the defect at all. So a second test ran the identical scenario with the regions **unnamed** and asserted the mark **moves**. It does. Only the pair is evidence: one shows the fix works, the other shows there was something to fix in that exact setup. Mutating the resolution path afterwards confirmed it from the third direction — the named lookup removed, the first test goes red.

**Principle**: When you fix a defect, write the test that fails without the fix *and* the test that reproduces the defect beside it. A green test for a fix is compatible with "the fix works", "the defect does not occur here" and "the test does not reach the code". Characterising the old behaviour in a test distinguishes them, and it keeps distinguishing them later: if the characterisation test ever starts passing by the old path becoming correct, the fix's test has quietly stopped meaning anything and you find out then rather than never.

### 6.50 Count the Thing the Code Counts, Not the Thing the Stylesheet Says (2026-10-11)
The region work needed a number: how many scrolling regions does the fleet have? Four answers came out of four predicates, each defensible, and only one matched what the code does. Declarations of `overflow` matching auto or scroll: 114. Distinct elements those declarations style: 111, because a component styles the same element under several parent variants. Elements whose class the component's own TypeScript creates: 104, because some selectors are dead CSS and some regions are built by rendered content. Elements that can carry a stable name: still 104, but only after checking each apparent exception by hand — two of the three I had written off as unnameable turned out to be nameable, and one turned out to be dead stylesheet rules rather than a region at all.

**Principle**: A count is a claim about the world, and the predicate is the claim. Before publishing a figure into a gate, a debt entry or an ADR, write down what single object you are counting and check that the code counts the same object. Then check the exceptions individually: a regex that fails to find a creation site is evidence about the regex, not about the code, and an exclusion inferred from a tool's silence will be wrong roughly as often as the tool is imprecise. This is 6.46 again, one measurement later, which is the point — the failure mode is not ignorance of the rule but the assumption that this time the obvious predicate is the right one.

### 6.51 A List Called "Pending" Will Hold Anything You Have No Word For (2026-10-11)
AuthCard sat in the fleet gate's `EXEMPT` list for two months. `EXEMPT` means migration pending, and nothing was pending: the re-measurement a day earlier had shown the factory signature was already container-first and the frozen Keycloak parity contract never needed touching. The reason it stayed is that the alternative list, `NOT_MOUNTABLE`, described four **shapes** — a service, an element builder, a boot script, a modal or docked overlay — and AuthCard is none of them. It is an ordinary component with an ordinary factory. What excludes it is **when** it renders: Dynamic UI composes a canvas in reaction to a model response, and AuthCard renders the login step that runs before any session exists, so there is no response for it to be part of and no moment at which a canvas could mount it. Shape-based criteria cannot express that, so a correct absence was filed as unfinished work. I had also reached the right answer by the wrong route, recommending exclusion because a model should not be able to place a login form — a policy the canvas would have to enforce, where the real reason needs no enforcement at all.

**Principle**: When something will not fit any category in a taxonomy, suspect the taxonomy before the thing. Lists named for a process state (`pending`, `todo`, `deferred`) are the default destination, so every category the exclusion list lacks becomes a false entry in the backlog, and it reads as work for as long as nobody re-reads it. Check the axis as well as the values: criteria about an object's shape cannot classify a constraint about its place in time, or in a sequence, or in a lifecycle. And when you arrive at a conclusion, check whether your reason is the load-bearing one — "we must prevent X" and "X cannot arise" recommend the same action and are not the same finding, and only the second one still holds after somebody changes the policy.

### 6.52 Name the Exact Capability You Lack, or the Gap Becomes Permanent (2026-10-11)
`markdownrenderer.test.ts` carried a section header reading `SEC-3: PLANTUML SVG SANITIZATION` and a describe block of the same name. SEC-3 is the defect where a PlantUML server's SVG reply reaches `innerHTML` unchecked. None of the three tests under that header touched a server reply. They checked `sanitize()` against SVG-shaped **markdown**, which is a different input on a different code path. One comment recorded why the real path was untested: `CompressionStream + fetch (unavailable in jsdom)`. I probed the environment and both exist. The only missing web API is `Blob.prototype.stream`, which the encoder calls and jsdom does not implement, and Node's own `Blob` has it. One `vi.stubGlobal("Blob", NodeBlob)` put the test on the real asynchronous path, after which a stubbed `fetch` could deliver a hostile reply and the defect could be characterised. The wrong reason had held the gap open for nearly seven months, and it reads as a law of the environment rather than a line somebody guessed.

**Principle**: When you record that something cannot be tested, name the exact API, call, or line that stops you, and check it. A plausible reason is worse than no reason, because a reader who sees "unavailable in jsdom" stops looking while a reader who sees nothing investigates. The same applies to the section heading: a test block named after a defect is a claim of coverage, and the claim outlives anyone's memory of whether the tests under it ever reached that defect. Name a block after the input it exercises, not after the ticket you hoped to close.

### 6.53 One Component, One Safety Property, Several Paths — Test Each Path, and Mutate to Find Out (2026-10-12)
`spinemap.test.ts` carried a section header reading `SEC-2: stripHtmlTags — XSS PREVENTION` and a describe block of the same name, with six tests. SEC-2 is the defect where a stored field value reaches `innerHTML` on a detached `div`. All six tests set a node **label** or **description** and then searched the SVG canvas for injected elements. They passed, and the property they checked is true: a label reaches the SVG through `textContent`, so markup in a label is shown as characters. But SpineMap handles consumer markup on more than one path, and `stripHtmlTags` is on a different one — it is called only from the `renderView` of two field adapters, which no test opened. "This component is safe against markup" is not one property. It is one property per path, and a test proving the easy path reads as proving all of them, because the component name, the defect name and the word in the heading all match.

The cheap way to find out is to break the function and see whether anything notices. Reducing `stripHtmlTags` to `return html` — no extraction at all — left **all 50** tests in the file passing. That run takes a few seconds, needs no reading, and answers a question that reading the tests had already answered wrongly once. Run it on the **unfixed** code, before the fix, or the measurement is about the new tests instead of the old ones.

**Principle**: Before trusting a test block that is named after a defect, mutate the function the defect is in to something obviously broken and run the suite. If nothing fails, no test reaches it, whatever the heading says — this is the identity-mutation probe, and it is the fastest question you can ask of inherited coverage. Then keep the misnamed tests and rename them, because a true assertion about a neighbouring path is still worth having; what has to go is the claim on the heading. Where one component applies the same-sounding guarantee on several paths, enumerate the call sites first and let that list, not the component name, decide how many tests you owe. Related: [[6.52]] on naming the exact missing capability, and insight 3.3 on suites that pass by collecting nothing.

### 6.54 A Probe That Reimplements the Harness Measures the Probe (2026-10-12)
To find out whether the fleet gate's fixtures were load-bearing, I wrote a probe that mounted each component twice — once with its fixture and once without — and compared the rendered output. The gate's own mount path is internal to `runtime/src/conformance.ts`, so the probe reimplemented it: the invoke convention, the `mountMethod` handling, the option merge. It reported five components whose fixture made no difference to what was rendered, and that looked like the finding I was after.

Every one of the five was the probe's own defect. Three threw `options.items is not iterable` because my option merge never got the fixture to the factory — and both mounts threw identically, which a signature comparison reads as "no difference". Two produced an empty host both times because my `mountMethod` branch did not attach them. The probe had rediscovered its own bugs and labelled them findings. Worse, the result contradicted a recorded measurement, which is the only reason I looked again instead of building on it.

The second attempt touched nothing but the real thing: empty one glue file's `options`, run the real gate, record whether it stays green, restore, repeat. Seventeen runs, no new code, and the answer was both different and trustworthy — seven of the thirteen mount fixtures were not load-bearing. The same technique then proved the fix, by swapping each fixture for an inert key.

**Principle**: When you need to know how a system behaves under a changed input, change the input and run the system. Do not build a second copy of the system to ask it. A reimplementation gives you two things that look the same in the output — the behaviour you wanted to measure, and your copy's divergence from the original — and nothing in the result distinguishes them. If the harness is too internal to drive from outside, that is an argument for putting the measurement *inside* it as a check, which is where this one ended up, not for cloning it. The corollary is a debugging rule: when a measurement contradicts one already in the record, suspect the new instrument before the old number. Related: [[6.53]] on mutating the real code to see whether a test reaches it.

### 6.55 A Count Is a Claim About a File Set and a Pattern — Write Both Down or You Have Neither (2026-10-13)

`console.log` in this repository was measured three times in the space of one
workstream: 406, then 200, then 176. The code did not change between them. The
number moved because nobody had written down which files were counted or what
was matched, so each measurement answered a different question and all three
were filed under one name.

WIN-1 shows the failure's end state. Its entry was re-measured as "311
occurrences on 203 lines in 113 non-test files". The file count was right. The
other two match no file set in the repository, and the casts they count are
byte-identical at every commit since, so the code cannot explain the gap. The
command was never recorded, so the error is now untraceable. The number cannot
be reproduced, corrected, or defended — it can only be replaced.

The instruments were part of the problem. One probe searched shipped bundles
for published API names and kept the trailing parentheses the documentation
writes, reporting seventeen real names as missing. A per-file count used
`grep -oc`, where `-c` silently overrides `-o` and counts matching *lines*.
That is almost certainly how a line count became an occurrence count in the
first place. Both bugs produced confident, specific, wrong findings.

Re-measuring also moved a verdict rather than a magnitude, which is the part
worth noticing. LOG-1 asked for `console.log` to become `console.debug`. Of
the 176 lines, 161 are the body of a logging shim where `console.log` is the
*correct* mapping for INFO, 10 are doc comment examples, 2 are sample code
drawn on a canvas as string data, and 1 is the log utility's own fallthrough.
Two are real call sites. The item was not 99 percent overstated. It was asking
for the wrong change, against a standard that another document had already
superseded. A stale count can hide a dead premise.

Two more came out of review, and both sharpen the lesson. The classifier had a
third bug: it tracked each quote type's parity separately, so an apostrophe
inside a double-quoted string left an odd single-quote count and filed a real
call site as string data. It was latent rather than active, which is only
knowable because the classification partition did not move when it was fixed.
And MRK-2 claimed 22 of 24 files in one directory lacked a marker when it is 2
of 29 — wrong by a factor of eleven, with the listing that proves it already
sitting in my own output from the MRK-1 measurement, unread for several steps.
Gathering evidence is not reading it.

**Principle**: A count is a claim about a file set and a pattern. State both in
code, where they can be read and re-run, not in prose where they decay into a
bare number. Classify what you count — a token in a comment, a string literal,
or a shim body is not a violation, and the difference is the whole finding.
Give the classifier a test, because a classifier is code and yours will be
wrong. Then ratchet the number so it can only fall, and date it so a reader
knows whether they are looking at a measurement or an old assertion. Related:
[[6.54]] on probes that measure themselves, and [[6.53]] on mutating the real
thing to find out whether anything notices.

### 6.56 Rehearsing a Pipeline Locally Tests the Commands, Never the Environment (2026-10-13)

Before wiring the structure suite into CI, I did what looked like careful work.
I read the suite's dependencies, confirmed the vendor step makes no network
call, confirmed every git command survives a depth-one checkout, and then ran
the exact CI sequence locally: full build, runtime typecheck, unit tests,
structure checks. Build 115 seconds, 4,955 tests, 32 of 32 checks, exit zero. I
also mutated a baseline to prove the new step could fail, which it did.

The first CI run failed anyway, on the step I had just rehearsed.

`scripts/check-fabricated-reads.mjs` imports `globSync` from `node:fs`, added
in Node v22.0.0. The workflow pinned Node 20, so check `[16]` threw a
`SyntaxError` before running a single assertion. That check could never have
passed in CI. It had been green since the day it was written, on a machine
running Node 26, and it had never executed anywhere else.

My rehearsal could not have found this. It ran on my runtime, which is the one
thing a local run cannot vary. Every command was right, every dependency was
present, the mutation proved the gate had teeth — and all of that was evidence
about the commands, not about the environment they would run in. I had
verified the half of the problem I could see from here and read the result as
verification of the whole.

The second-order lesson is about the item I had already written. I opened a
tracker entry for the version gap saying it "needs a run to find out, not a
guess", and then treated my local run as that run. A local rehearsal is the
guess. Knowing the right epistemics and then substituting the convenient test
is the easier mistake to make than not knowing them.

There was a third instance in the fix itself, caught in review. I declared
`engines.node >= 22` in `package.json`, because 22 is where the Node
documentation says `globSync` was added. Nothing in this repository has ever
run on 22 or 23, and the API was experimental until 22.17.0, so the declaration
promised support for a range nobody had exercised. In a change whose whole
argument is "state the preconditions you measured", I wrote down a
documented number and presented it as a measured one. The floor there is
evidence for is 24, which CI and production both run.

**Principle**: A pipeline has two halves — the commands and the environment.
Running the commands locally tests the first and silently inherits your own
version of the second. Pin the environment to what ships, declare the floor
where tools can read it (`engines` in `package.json`, not a comment), and
accept that the only test of a CI environment is a CI run. When a check has
only ever passed on one machine, you do not know that it passes. Related:
[[6.35]] on a check that cannot fail, and [[6.55]] on stating a measurement's
preconditions instead of trusting the number.

### 6.57 Refactoring the Code a Check Reads Can Turn the Check Green by Blinding It (2026-10-13)

LOG-2 asked me to migrate 26 component files onto the mandated logging
pattern. Nineteen of them belonged to DiagramEngine, where 20 log prefixes
each carried four near-identical helper functions. Repeating the mandated
preamble 20 more times would have added 291 lines to the largest file in the
repository, so I replaced the duplication with one factory and had each module
destructure the levels it uses. 80 helper declarations and 294 lines removed
from the modules, all 118 call sites left standing,
every test passing, and the size ratchet moved in the right direction.

The check that measures logging conformance then reported zero violations and
passed. It was wrong. Those 17 modules no longer contained the token the
classifier looks for, so 17 files holding 57 log calls between them classified
as "no-logging" — not conforming, not violating, invisible. The count was
correct by accident and the gate had quietly stopped watching the largest
component in the repository.

Nothing failed. That is the whole problem. A broken check announces itself. A
blinded one reports success. The classifier had tests, and they all passed,
because every test exercised a form of code the classifier still recognized.
The refactor did not break a rule the tests encoded, it moved the code outside
the universe the tests described.

**When a change alters the shape of what a check reads, the check's silence is
not evidence.** Re-derive the classification by hand for at least one affected
file and confirm the classifier agrees. Here that meant printing the per-file
verdicts rather than the totals, where 17 lines of `no-logging` against files
I had just edited were impossible to miss.

The reviewer predicted this before I ran it, from the refactor's shape alone:
remove the token a classifier keys on and the classifier goes quiet. That is a
general shape, not a detail of this codebase. Related: [[6.35]] on a check that
cannot fail, [[6.55]] on a count being a claim about a file set and a pattern,
and [[6.56]] on verifying the half of a problem you can see.

### 6.58 A Standard That Contradicts Itself Produces Code That Follows Neither Half (2026-10-13)

Two documents governed logging here. LOGGING.md said to use `console` directly
and not to create a shared logger. FRONTEND_LOGGING.md shipped a shared logger
as a component and required every component to route through it. AGENTS.md
pointed at the first one. 117 files followed the second, 24 followed half of
it, and 2 followed neither.

I expected to resolve that by naming an authority, which took one paragraph in
each document. The work was elsewhere: the winning document contradicted
*itself* in four places, every one of them text copied from the document it
superseded. It told the reader to prefer `console.log`, to strip
`console.debug` before committing, that "we use `console.*` directly", and to
include correlation IDs that its own section 8 assigns to the host
application. A document assembled by copying its predecessor inherits the
predecessor's rules along with its prose.

The second finding was worse, because it was in the prescribed code. The
snippet every component is told to copy carried two `(window as any)` casts.
Using it 26 more times would have added 52 occurrences to the very count
another open item tracks, and the structure suite would have rejected the
change for violating one standard while complying with another. The snippet
also ran 148 characters wide against a documented 120-character limit, in 108
files. (Both of those figures were wrong when first written, as 133 to 150 and
117. Measured on 2026-10-14: the one-line form was uniformly 148 characters in
108 files, and 2 further files already carried it across three lines.) A mandated snippet is code, and nobody had reviewed it as code.

**Before migrating N files onto a pattern, check the pattern against the other
standards it has to satisfy.** The migration is the cheap part. Declaring the
window globals in one `.d.ts` cost four lines and turned a 52-occurrence
regression into none. Related: [[6.55]] on counts as claims, and ADR-171.

One last instance of the same error, in the commit that closed this item. I
reported "192 call sites unchanged" in six places. The real figure is **118**,
and 192 was neither a call-site count nor correct: the regex I counted with
matched the helper *declarations* as well as the calls, and its character class
excluded underscores, so it missed six real names in `tool-text.ts` — the same
blind spot that made my migration script skip that file. The true before-and-
after is 198 matches falling to 118, which decomposes as 80 declarations
removed and 118 calls standing. The reviewer caught it by asking the obvious
question: the count was taken before the change and never retaken. **Restating
a measurement after the thing it measures has changed is not restating, it is
asserting.** See [[6.55]]: the pattern is half the claim, and a regex that
matches more than you think is how a count becomes a different count with the
same name.

### 6.59 Byte-Identical Compiled Output Is the Proof That a Type-Only Change Is Type-Only (2026-10-14)

WIN-1 phase A changed 110 files. It replaced `(window as any).createLogUtility`
with `window.createLogUtility` and reflowed one line into three. Every edit was
supposed to touch types and whitespace only. The 4958 unit tests passed, which
is the usual evidence, and it is weaker than it looks: a passing suite says the
paths the tests cover still behave the same. It says nothing about the paths
they do not cover.

**For a change that claims to be type-only, build before and build after, then
diff the emitted output.** All 126 compiled bundles came back byte-for-byte
identical. That is not evidence about covered paths. It is evidence that no
path changed, because the program the browser runs is the same program. The
check cost one `cp -R` and one `diff -rq`, and it is available for any refactor
whose whole claim is that the runtime does not move: a rename, a cast removal,
a reflow, an `import type`. When the diff is not empty, the claim was wrong and
the suite would not have told you. Related: [[6.54]] on probes that measure
themselves.

### 6.60 A Ratchet Gates the Total and Says Nothing About What the Total Is Made Of (2026-10-14)

WIN-1's measured count of 294 was correct, re-derivable, and gated by check
`[20]`. The paragraph underneath it, explaining what those 294 casts *were*,
was wrong twice. It listed `MathfieldElement` among the remaining third-party
globals, and all 3 of its casts live in a test file the counted file set
excludes, so it was never in the 294 at all. It also framed the item as unsafe
reads of other components' globals. When the mechanical half was removed and
the remainder could be read directly, 66 of the 74 survivors turned out to be
each component publishing its own API to `window`, and only 7 were
cross-component reads. Every one of those 7 already guarded with `typeof`.

**The breakdown of a count is a separate claim from the count, and only one of
them is under the ratchet.** The number was protected by a check that reruns on
every commit. The sentence describing its composition was protected by nothing,
so it aged the way the March 2026 figures aged. Before scoping work from a
tracker entry, re-derive the composition, not only the total — the total tells
you how much there is and the composition tells you what kind of work it is.
Here it was the difference between "20 declarations and no behavior change" and
"audit every cross-component lookup in the library". See [[6.55]]: a count is a
claim about a file set and a pattern, and so is every sentence that explains it.

### 6.61 A Ratchet Is Only as Wide as Its Pattern, and a Narrow One Builds a Blind Spot Bigger Than Itself (2026-10-14)

WIN-1 counted `(window as any)`. The count was gated by check `[20]`,
re-derivable from code, mutation-proven, and correct. It went from 294 to 0 in
two days. Reading the last 74 to plan the work turned up the thing the count
could not say: the library asserts on `window` in **four** spellings, and the
one WIN-1 watched was the smaller population. 74 `any` against 248
`unknown as Record<string, ...>` and 3 inline or line-wrapped. **The unwatched
population was 3.3 times the watched one, and a cast in any spelling but `any`
could be added for free while the gate reported progress.**

Nothing here was a measurement error. The file set was declared, the pattern
was declared, the number was reproducible. The pattern simply answered a
narrower question than the item's name — "window cast pattern" — implied, and
nobody had asked what else satisfies the name.

**When a count gates a behavior, write the pattern against the behavior, not
against the spelling you first saw.** The concrete test: before trusting a
count to zero, ask what *else* would satisfy its English description, then grep
for the general form. Here that was `window as ` — four characters shorter than
`window as any` and 4.4 times the hits. The total is now gated and the
breakdown by asserted type prints ungated, so a spelling that moves is visible
without being a failure.

Two mutations show the difference, and the second is the whole insight:
rewriting one `record` cast as an inline object type holds the total and shifts
the breakdown, while adding a cast in a new spelling raises the total and
fails — and leaves `windowAnyCasts` at 0, passing. Related: [[6.55]] on counts
as claims about a file set and a pattern, and [[6.58]], because renaming the
count rather than opening a new one would have produced a different count with
the same name.

### 6.62 Migrating by Grep Migrates What You Grepped For (2026-10-14)

WIN-1 phase A moved the LogUtility lookup to the declared global in 110 files
and reported the preamble as migrated. It searched for
`(window as any).createLogUtility`. Six components reached the same global
through four other spellings and were invisible to that search, and
`components/logutility/logutility.ts` — the component that **publishes**
`createLogUtility` — registered it through a double cast, so the producer of
the typed contract was not using the contract.

The counts stayed honest, because they count casts rather than claims. The
prose did not: "all 110 now reach the global through the declaration" is true
and reads as "the lookup is now uniform", which was false for seven files.

**Search for the subject, not for the syntax.** One `grep -l createLogUtility`
over the tracked sources returns 126 files and ends the question in a second,
where the cast-shaped search returned 110 and felt complete. The general rule:
when migrating every use of X, enumerate by X and then classify, instead of
enumerating by the shape you expect X's uses to have. The shape is a hypothesis.
The name is the fact. This is the same failure as the character class that
excluded underscores in [[6.58]], one level up: there the pattern was too narrow
for the names, here it was too narrow for the syntax.

### 6.63 Removing a Cast Can Unpublish an API, and the Check That Watches the API Will Not Notice (2026-10-14)

`extractGlobals` in `scripts/generate-docs.js` finds the names a component
registers on `window`. It recognized a cast by its parentheses and a bare
`window` by dot access. WIN-1 phase B removes the parentheses from 38 bracket
registrations, which leaves `window["Toolbar"] = Toolbar` — a line neither rule
matches.

Measured before the conversion ran, by reverting the extractor fix and
regenerating: **14 components report `Globals: none` and 38 published names
disappear** from the quick reference. `scripts/check-published-api.mjs`, check
`[19]`, **passes through all of it**, because it verifies that every published
name exists in the built artifact. A name that stops being published is not a
name it checks. The guard against fiction had no guard against silence.

**A check that validates the entries on a list cannot tell you the list got
shorter.** Pair any "everything published is real" check with a count, or
with the diff of the generated output against a snapshot. Here the snapshot

the only differences to be ones you can name. Related: [[6.57]], where
refactoring the code a check reads turned the check green by blinding it. This
is its sibling — refactoring the code a *generator* reads empties the generated
file, and the check downstream of it still passes because its question was
never "is this complete".

### 6.64 A Filter That Excludes `*.test.ts` Does Not Exclude `tests/` (2026-10-14)

`scripts/audit-counts.mjs` stated its file set in a comment: tracked
TypeScript sources, "no test or spec files, because a violation in a test is
not a violation in the library". The printed header said the same. The filter
was `!/\.(test|spec)\.ts$/`, which matches a file CALLED a test and says
nothing about a file that LIVES in the test directory. `tests/setup.ts` and
`tests/helpers/dom-helpers.ts` were inside every count for as long as the
comment claimed they were not.

Nothing downstream noticed, because the two files contribute exactly one
occurrence to any counted pattern. The cost was not a wrong number. It was a
wrong inference: `CODEBASE_FIXES.md` reasoned from the stated set and
concluded that the single `(globalThis as any)` in `tests/setup.ts` was
"outside the count twice over", which was false twice.

**A file-set comment is a claim, and a claim about code is testable.** The
set is stated in one place and implemented three lines below it, and the two
still disagreed for a month. Read the filter, not the paragraph above it,
and prefer a directory exclusion to a name pattern when the intent is "test
infrastructure" rather than "files named like tests". Related: [[6.59]].

### 6.65 An Alias Spends One Occurrence and Buys Unlimited Access (2026-10-14)

WIN-2 was scoped at 237 occurrences of `window as `. The real conversion
surface was 310, and the gap was one line:

The counted pattern appears once. Every access after it is free. Measured

### 6.66 A Check Script Is Code, and an Inline One Is Code You Did Not Read (2026-10-14)

While closing WIN-2 I ran an inline `node -e` check for whether 25

missing. That matched a prediction made minutes earlier, so I converted 11

All 25 names were present. `extractGlobals` had handled aliases since WIN-1,
at `scripts/generate-docs.js:421`. The check was wrong: `\\\\b` written inside
a single-quoted bash string reaches the RegExp constructor as a literal `\b`,
which matches a backspace character, so no name could ever match. A `grep`
for one name would have shown it in two seconds.

Two things made it land. The result **confirmed a prediction**, and it was
**too clean** — exactly 25 of 25, with nothing partial. A real gap in a
generated document is almost never total.

**A measurement that agrees with your hypothesis deserves a second method
before it earns an edit.** Write check scripts to a file where the escaping
is visible and can be read back, and confirm a surprising negative with a
different tool than the one that produced it. This is the second
inline-escaping failure in this arc; the first mangled a regex in a
counterfactual probe. Related: [[6.63]], where the counterfactual was run
correctly and was worth everything.

### 6.67 Three Ratchets, Three Blind Spots, One Shape (2026-10-14)

In three days this repository found the same defect three times, each one
level further out than the last:

| Count | Watched | Missed | Ratio |
|---|---|---|---|
| `windowAnyCasts` | `window as any`, 74 | three other spellings, 251 | 1 : 3.4 |
| `windowCasts` | every assertion, 237 | the alias carrying 73 uses, 73 | 1 : 0.3 |
| `anyAnnotations` | `: any`, 88 | `as any`, 69 | 1 : 0.8 |

Each gate was correct, re-derivable, mutation-proven, and named after a
behavior it only partly watched. The third one is the clearest: `: any` is a
DECLARATION saying the type is unknown, `as any` says the same about an
EXPRESSION, and the only difference between them is a colon. Nobody set out
to exempt casts. The pattern was written by looking at the code in front of
it, and the code in front of it used annotations.

**A count named after a concept will be read as covering the concept.** The
name is the claim the next reader believes, so the pattern has to earn it.
Before baselining anything, write down the behavior in a sentence with no
syntax in it, then ask how many ways the language has to express that
sentence. For "reaching the global object untyped" the answer was four
spellings, plus an alias, plus `globalThis`. For "telling the checker you do
not know" it was two, plus `@ts-expect-error`, plus an implicit `any` from a
library signature that no text pattern can see at all.

Related: [[6.60]], [[6.61]], [[6.65]]. The fix each time was not a wider
regex. It was a SECOND count beside the first, because the two then disagree
when a cast is rewritten as an annotation, and one of them fails.

### 6.68 A Cast Is Usually Downstream of a Type That Was Never Written (2026-10-14)

`components/toolbar/toolbar.ts` held 56 `as any` casts, 41 of them
`(config as any).<field>`. The obvious reading is that someone was lazy 41
times. The real cause was one line:

```typescript
private toolConfigs: Map<string, ToolItem | SplitButtonItem | GalleryItem>
```

The file declares TEN item interfaces. The map named three, and the seven it
omitted are exactly the ones carrying `checked`, `value` and `suffix` — the
fields the casts were reaching for. Nothing failed, because `addTool` stores
`JSON.parse(JSON.stringify(tool))` and `JSON.parse` returns `any`, so the one
line that fills the map launders the type and the declared union is never
checked against what is actually stored.

The same shape appeared twice more the same day. DockLayout described five
slots as `any` when the twelve members it calls on them are identical every
time. Eight layout components each described the mounted child as `any` when
the surface is the same seven members in all eight.

**Count the casts, then look for the one declaration upstream of all of
them.** 41 casts, 1 missing union. 26 annotations, 1 missing interface. 16
annotations across 8 files, 1 missing shared contract. Fixing the
declaration removed the casts as a side effect, and in the DockLayout case
all 126 compiled bundles stayed byte-for-byte identical, which is the proof
that nothing but the types moved.

The corollary is a warning. A JSON round trip, a library function returning
`any`, or a `@ts-expect-error` will hide a wrong type indefinitely and none
of them is visible to a text-pattern count. This repository had exactly one
`@ts-expect-error`, and it was hiding a crash: `ErrorDialog.show()` called
`new bootstrap.Modal(...)` with no guard, so a page without Bootstrap's
JavaScript got a `ReferenceError` out of the dialog whose job is to report
that something already went wrong.

### 6.69 "Safe to Leave In" Is a Claim About Emission, Not About the Viewer's Filter (2026-10-14)

`FRONTEND_LOGGING.md` justified shipping debug calls to production with:

> Browser DevTools hides debug output by default, so this is safe to leave
> in production builds.

That sentence is true and the conclusion does not follow. DevTools hides
`console.debug` from the **default display filter**. The call still runs,
still builds an ISO timestamp, still formats its arguments, still enters the
console buffer. Anyone who ticks "Verbose", attaches a remote debugger, or
reads a captured console sees all of it, and in this library that was 385
`logDebug` call sites across 131 components.

The repository then had a real filter, and the sentence was what kept
anybody from noticing that **the filter was not reached on the path most
pages take**. The utility gated debug by level; the fallback that runs when
the utility is absent gated nothing at all, and 132 of 138 demo pages take
the fallback.

**A control you cannot see the code for is not a control you have.** When a
document says output is suppressed, find the line that suppresses it. If
the line lives in someone else's tool, the suppression is a convention of
that tool and not a property of your program. The fix is one your own code
can state: the emitter decides, and the viewer's filter is a convenience on
top.

The same reasoning applies to the default. `level: "debug"` was the
documented default, so debug emitting was deliberate in the sense that
somebody typed it — and nobody had asked whether the default should be the
verbose one, because no page ever configured a level and so nothing ever
surfaced the choice.

### 6.70 Migrating One Pattern Across a Codebase Means Finding Out It Is Four Patterns (2026-10-14)

LOG-3 had to gate a one-line logging shim in 117 files. The first script
matched the shape that appears in 109 of them and reported success. Eight
files were untouched, and a second script found three more shapes: a ternary
split across lines, an if/else block, and NavRail's early return. The last
one was edited by hand.

A script that assumes uniformity does not fail on the files it does not
recognize. It skips them and reports the number it did change, which reads
exactly like completion.

**The check caught it, and only because the check was written first.** This
is the same ordering the last three items used, and here it paid in a new
way: `ungatedVerboseShims` was baselined at 225 before any file moved, so
after the first pass it read 9 rather than 0 and said which files. Without
it the migration would have reported "115 files migrated" and been believed.

**Then the checker turned out to have the same bug.** It read a shim body
with a lazy `[^}]*`, which stops at the first `}` — for the if/else shape
that is the brace closing the `if`, so a gate written in the `else` went
unseen and four files that HAD been migrated counted as unmigrated.
Anchoring to `\n}` fixed those four and broke the one-liners, where the
closing brace is on the same line. Counting braces reads all four shapes.

The pattern that matches your code and the pattern that verifies your code
are the same pattern, so they are wrong in the same way at the same time.
Write the verifier to parse rather than to match whenever the thing it reads
has more than one shape — and expect to learn how many shapes there are from
the verifier disagreeing with you.

### 6.71 Every Ratchet Was a Ceiling, and the Defect Was an Absence (2026-10-15)

`scripts/audit-counts.mjs` tracks eighteen counts. Each one caps something
unwanted and fails when the number goes up. That shape found four real
defects in this arc, so it felt general. It is not.

DiagramEngine's published type file held one usable name out of 138,
because the build script deleted every `export` keyword before the compiler
read the file. Nothing could see it. There is no count of a thing that is
missing, and every existing count would have read as healthy forever.

The fix was a `FLOORS` table: counts that fail when they FALL. One entry so
far, `diagramengineBundleExports`, pinned at 138 and mutation-proven by
restoring the strip and watching it read 0.

**Before adding a check, ask which direction the failure moves in.** The
four earlier misses in this arc were patterns that matched too little, and
widening the pattern fixed each one. This one was a ceiling where a floor
was needed, and no amount of widening would ever have reached it.

A second lesson sits underneath. The strip was `s/^export //g`, a
substitution. It rewrites a line and never removes one, so
`diagramengineLines` sat unchanged at 30482 through the entire regression.
**A line-count ratchet is blind to any edit that trades one token for
another**, which is most of what a damaging edit actually does.

### 6.72 A Tracker Entry Can Be Wrong in the Direction That Makes It Worse (2026-10-15)

STD-1 and STD-2 were the last two entries under CRITICAL — Standards, open
since March 2026. Both were wrong, and they were wrong in opposite ways
that are both worth recognizing.

STD-2 asked for a change that would have **damaged** the codebase. It named
ten implementation classes and asked for an `export` keyword on each. All
ten sit behind an exported options type, an exported handle, and an
exported factory. They are the encapsulation that PAT-1, in the same
document, asks every component to adopt. Doing STD-2 would have published
implementation details in order to satisfy a rule invented for the entry.

STD-1 was wrong about the diagnosis while **standing on a real defect**. It
saw no export keywords and called it a standards violation. The keywords
were stripped on purpose by a generator, which makes the complaint
baseless, and the strip also destroyed the published type surface, which
makes it the most serious defect in the section. An entry can be
simultaneously incorrect and pointing at something.

The common cause is that both entries reasoned from a text pattern to a
conclusion without reading the build. `diagramengine.ts` is generated. Its
header says so on line 11.

**When an entry has been open a long time, re-derive its premise before
its fix.** The premise is what rotted. In this arc that has now happened to
`UNUSED-1` (119 to 421), `MRK-1` (12 to 3), `MRK-2` (22 of 24 to 2 of 29),
`IMP-1` (47 to 113), `DEBT-SEC-3`, and now both STD entries. The pattern is
strong enough to be the default assumption.

### 6.73 Measuring an Entry to Close It Can Reopen It Much Larger (2026-10-15)

Closing STD-2 required knowing how many factories leak an implementation

question in one line: one factory returned a class nobody could name, and
STD-1 had already fixed it.

Then the same scan was pointed at the next question over, which is whether
a factory returns a class at all. **83 of 130.** PAT-1 describes this as
"some components" and is filed under MINOR. It is the majority of the
public API, and it had never been counted in the seven months the entry was

The number was two lines of extra code in a script written for another
purpose. **The reason a vague entry stays vague is that nobody measures it,
and the reason nobody measures it is that it is filed as MINOR.** Severity
recorded before measurement is a guess wearing a label.

### 6.74 Where the Call Goes Was the Whole Problem (2026-10-15)

Instrumenting 106 components with trace sounds like a loop over files. The
transform's first honest run refused 112 of 250 listener sites and reported
"handler body is an expression, not a block", which read like a limitation
of the tool.

It was a description of the codebase. **99 of 229 sites attach a handler by
reference**, `addEventListener("pointermove", this.boundMove)`, and the
commonest remaining shape is a thunk, `(e) => this.onKeydown(e)`. Inserting
at the registration site would have missed the first group completely and
written the trace into a one-line wrapper for the second, leaving the
function that actually runs untouched and the count looking finished.

The fix was to resolve each listener to the function that runs, through
`.bind(this)`, name aliases and thunks. **The guard mattered more than the
resolution.** Following any one-line delegation reached helpers whose first
parameter was a `string` or a `number`: four handlers would have been
labelled as input events inside shared methods with other callers. Requiring
that the wrapper forward its own event argument, or that the callee be
referenced exactly once, caught all four.

A transform over 250 sites is worth building only if it refuses. The 24
refusals were the deliverable as much as the 222 insertions, because each
one was a case a regex would have silently got wrong.

### 6.75 Instrumentation Nobody Can Switch On Is Not Instrumentation (2026-10-15)

Reading the gates before adding trace to them turned up a sentence in

toggling one in the browser console takes effect immediately, which it
offers as the customer-support story.

It is true on the LogUtility branch. On the fallback branch `const _trc` is
evaluated once when the script loads, and **109 components capture it that

ADR-176 decided what the flags mean and never decided when they are read,
so this is drift and not a choice. Two things follow. The first is that it
belongs in its own entry, because it affects debug identically and fixing it
inside a trace change would be scope creep dressed as diligence. The second
is that a documented promise found to be false is not a neutral thing to
leave alone while the entry waits: section 6 now carries a caveat pointing

moment they need it.

### 6.76 A Column Limit Measured in Bytes Is Not a Column Limit (2026-10-15)

LOG-5 said 531 shim lines exceed the 120-character limit and nothing
enforces it. Adding the ceiling meant counting what was there, and the
first count disagreed with the second by a third: `awk 'length > 120'`
reported 928 where the new check reported 819, at the same commit.

awk counts bytes in the C locale. Every marker header in this repository
carries ⚓, 📜, 🔗 and ⚡, and each of those is three bytes and one column.
So the tool that was easiest to reach reported a file as over the limit for
characters nobody can see in a column, and would have failed a ratchet for
them.

**A limit stated in one unit has to be measured in that unit, and the
easiest tool does not always use it.** The version that matters is the one
the rule is about: 120 is what a reader counts across a screen, so the
check counts characters, and the baseline is 288 rather than 397. The two
numbers differ by 109, which is the emoji in the headers and nothing else.

The related trap is quieter. Had the ceiling been baselined from awk at
397, it would have passed on the day it was written and then failed later
for an unrelated file that happened to carry a marker, with a diff that
showed no long line at all.

### 6.77 The Fix Put a New Name in Every File and the Generator Published It (2026-10-15)

LOG-6 added `const f = window.__ebt_debug_logging;` to 117 component
preambles. The unit tests passed, the structure checks passed, and
`docs/AGENT_QUICK_REF.md` came out of the build with six new entries under
auditlogviewer: `action()`, `actor()`, `dateFrom()`, `dateTo()`, `search()`
and `severity()`, advertised as callable CDN API.

`extractGlobals` follows a local that aliases the global object, so that
`const w = window as Record<string, unknown>` and a later `w.createThing =`
are reported. Its pattern for that was `= window\b[^;]*;`, which also
matches a property READ. The new `f` became an alias, and auditlogviewer's
own assignments to its own `f` were published.

It was already wrong before LOG-6 touched anything.
`const style = window.getComputedStyle(el)` reads identically, so fourteen
CSS property names from smarttextinput, `border`, `font`, `padding`,
`whiteSpace` and the rest, had been sitting in the published reference as
callable globals. Twenty names in all that were never API.

**Two things did the work here, and neither was a test.** The first is that
generated output is committed, so a build produces a diff and the diff gets
read. The second is that the change was uniform: putting one new identifier
into 117 files is a wide, shallow perturbation, and a latent pattern bug
that needs a coincidence to fire gets 117 chances at once. `test-local.sh`
check [19] verifies every published name EXISTS. Existence was never the
problem, and a check written against absence cannot see a surplus — the
same shape as the floors, from the other side.

### 6.78 The Mutation That Moved Nothing Was the Useful One (2026-10-15)

LOG-4a finished with four counts green: 109 traced components, three
ceilings at zero. Proving them meant breaking them, and the first attempt
broke nothing. Deleting four of diagramengine's five trace calls left every
count sitting exactly on its line.

The fifth call is in `src/render-engine.ts`. `tracedComponents` counts
COMPONENTS, and one surviving call keeps a file in the traced bucket. So a
30,524-line file could lose 80 percent of its instrumentation and the
ratchet would report success.

**The floor was correct and its unit was wrong.** It was built during LOG-4,
when the question was whether a component had any trace at all, and that is
a per-component question. Instrumenting a bundle changed the question
without changing the count, and nothing announced that, because a count
keeps reporting confidently in the units it was born with.

`traceCalls`, a floor at 301, is the fix and it took four lines. The
expensive part was running a mutation expecting a failure and getting a
pass, then believing the pass rather than moving on.

**A mutation test has two outcomes worth having.** The count fails, which
confirms it watches what it claims. Or the count does not fail, which is the
more valuable result, because it is the only cheap way to find out that a
guard has quietly stopped matching the thing it guards. The ones that pass
are the ones to write down.

### 6.80 Scoping the Decision Found the Thing That Needed No Decision (2026-10-15)

DEBT-SEC-5 asks a real question: should five optional renderers join the

### 6.81 The Marker Was There in Prose and Missing in Shape (2026-10-15)

Seven files were recorded as missing the `COMPONENT` marker. Not one of
them was undocumented. `treegrid.ts` opened with a banner reading "TreeGrid
Component - Phase 1". The two engine files had a `/** DiagramEngine — … */`
paragraph describing exactly what the block form describes. All four SCSS
files had `/* ⚓ SymbolPicker — grid-based symbol / icon picker … */`, which
carries the anchor emoji and not the keyword.

A reader opening any of the seven would say it was marked. The check said
otherwise and the check was right.

**A convention has two jobs and these files were doing only one.** The
information was present for a human reading top to bottom. The SHAPE was
absent, and the shape is what makes the information findable by something
that greps rather than reads. MARKERS.md exists for the second job. Four of
the seven had the emoji and not the keyword, which is the signature of a
convention adopted by eye: the part that looks like the convention got
copied and the part that does the work did not.

**Fixing it is also when you find out the count was honest.** It would have
been easy to read these as false positives and relax the check to accept
`⚓` anywhere. That would have taken the number to zero and removed the only
thing that can tell a marked file from a decorated one.

### 6.82 An Unratcheted Count Is a Memory of a Measurement (2026-10-15)

UNUSED-1 was the last tracked count in this repository with no ratchet,
because it needs the compiler rather than a scan. The entry said to
re-derive it by hand and recorded **414**, measured on 2026-10-15.

The real number that same day was **308**.

106 of the difference were LOG-4's dead `logTrace` declarations. TS6133
counts an uncalled function like any other unused binding, so instrumenting
94 components and deleting 12 shims cleared 106 errors nobody was counting.
Measured rather than assumed: a worktree at `e361179` reports 414 of which
106 name `logTrace`, and the tree after LOG-4 reports 308 of which none do.
414 − 106 = 308, exactly.

**A quarter of a tracked count vanished as a side effect of unrelated work,
on the day it was re-measured, and nothing noticed.** Not because anybody
was careless — the number was measured carefully and written down carefully.
It went stale four commits later because nothing was watching it.

**That is the whole argument, and it is the opposite of the intuitive one.**
The reason given for not ratcheting this count was that it is expensive to
derive: it needs `tsc` rather than a grep. Expensive to derive is precisely
why it must be automated, because expensive is exactly what nobody repeats.
The cheap counts can survive being checked by hand. This one could not, and
it is 1.6 seconds.

### 6.83 A Heading Is a Claim About Population, and Nothing Checks It (2026-10-15)

The tracker section reads "`!important` in Component SCSS (113
occurrences, 20 files)". The count behind it spans every tracked `.scss`
in the repository, so **58 of the 113 are not component stylesheets at
all, and 56 of those 58 are in one file**, `src/scss/_dark-mode.scss`,
where beating Bootstrap's specificity is the exact third-party override
the style guide permits.

The real target is 29 declarations in 8 files. The headline said 113, so
the item read as four times its size and as spread across the fleet rather
than concentrated.

This is the third time: `anyAnnotations` watched declarations and missed 69
casts, `WIN-1` watched one spelling of a cast, and now a count headed
"Component SCSS" measures every stylesheet. **Each time the count was
correct and its NAME was the thing that was wrong**, and a name is not
executable, so nothing can fail when it drifts from what is measured. The
only defence found so far is to re-derive the population whenever the

because a heading looks like it was checked.

### 6.84 Allman Braces Break Every Brace-Counting Scan (2026-10-15)

Classifying the 54 `!important` declarations by justification needed to
know which sit inside `@media (prefers-reduced-motion: reduce)`. The first
scan tracked nesting depth per line and recorded the depth on the line that
matched `prefers-reduced-motion`.

This repository writes Allman braces, so that line has no `{` on it. Depth
had not risen when it was recorded, the very next check saw `depth <=
rmDepth`, and the block closed itself on the line it opened. **Three whole
files of accessibility overrides were classified as unjustified**, and the
split came out 8 and 32 instead of 11 and 29.

It was caught by spot-checking one file by eye before writing the numbers
down, not by the scan failing. The scan was confident.

**The assumption was invisible because it is true in most codebases.**
`if (x) {` puts the brace on the introducing line, and a scanner written
anywhere else works. Here it never does. Every brace-counting pass over
this codebase has to wait for the opening brace rather than assume it
arrives with the construct, and it is worth checking any existing scan that
tracks nesting for the same mistake.

**The general shape: a scanner written against a language is wrong when the
codebase has a dialect.** The style guide is a fact about the input, and a
scan that has not read it is guessing.

### 6.85 A Fallback Is a Bug That Passes Its Own Tests (2026-10-16)

Ten SpineMap adapters mounted a bare text input when a library picker was
missing. Nine of them worked, in the sense that a user could type and the
value came back. Three did not: `multiselectcombo`, `tagger` and
`peoplepicker` read through `getSelected()` and `getTags()`, while the
stand-in supplied `getValue()` only. Those three **discarded every keystroke
and answered `""` or `[]`**.

Nothing caught it. The instance is typed `Record<string, Function>`, so the
mismatch between the method the stand-in supplies and the method the adapter
reads is invisible to the compiler. No test asserted the fallback, because a
fallback is what happens when the test environment is incomplete, and the
test environment was complete. The only runtime trace was a `logWarn`.

**The failure mode is specific to fallbacks.** Real code is exercised, so a
drift between two sides of it gets caught. A fallback runs only when
something else is already broken, which is exactly when nobody is watching.
It rots silently and then answers confidently.

**This is the argument for letting it break that the policy argument misses.**
"Fail loudly" is usually defended on debuggability. The stronger reason is
that a fallback is a second implementation with no users, and a second
implementation with no users is wrong by the time it runs.

### 6.86 A Gate Anchored on a Keyword Cannot See the Other Grammar (2026-10-16)

`check-fabricated-reads.mjs` walks the TypeScript AST precisely because a
regex could not tell whether a `return` sat inside a `catch`. It was right
about that and it still missed all ten adapters, because every probe in it
begins `ts.isReturnStatement(node)`. The adapters did not return a
fabrication. They **assigned** one, from a method whose own failure context
was in the caller:

```ts
catch { this.fallback(wrap, value); }          // the failure branch

private fallback(wrap, value) {
    this.instance = { getValue: () => inp.value };   // the fabrication
}
```

Two separate things defeated it. The grammar was assignment rather than
return, and the failure context was one stack frame up. ADR-157 had
enumerated three shapes and recorded two known gaps, and this was a fourth
shape that none of them described.

**Moving from regex to AST raises the floor and does not change the
question.** Both ask "does this keyword appear in that context". A
fabrication is a semantic event, and it has at least as many grammars as
JavaScript has ways to put a value somewhere.

**The honest way to report the fix is the one that admits the residue.** The
extended gate catches 9 of the 10. SymbolPicker escapes, because it
fabricated through `this.selected` rather than an object literal. Reporting
10 of 10 would have turned a ratchet back into a clearance.

### 6.87 The Fix That Satisfies Four Ratchets by Breaking Three Others (2026-10-16)

The first version of the shared helper opened with
`const win = window as unknown as Record<string, unknown>`, copying the

WIN-2 had driven those three from 237, 42 and 73 down to 6, 1 and 1. The

**Deleting code is where a ratchet is most likely to be surprised.** The
instinct when removing a bad pattern is to lift what the bad code did into
the replacement, and what it did was itself a tracked debt. The counts
noticed. Nothing else would have.

### 6.88 A Fallback Is Where Two Implementations Drift Apart Unwatched (2026-10-16)

The full sweep found the same defect shape four times, in four unrelated
components, and in every case the fallback *looked* right:

- `multiselectcombo`'s stand-in exposed `getValue()`, the adapter read
  `getSelected()`. Every keystroke discarded.
- Both copy buttons called `execCommand("copy")` and never read the
  boolean it returns, then showed a success tick.
- MarkdownEditor's display fallback put **markdown** into `innerHTML` and
  called `fireDisplayReady()`.
- FormDialog's dirty-close fallback called `doClose()` directly.

None had a failing test. None had a bug report. The fallback is a second
implementation of a path the first implementation also serves, and only
one of the two is ever exercised. The unexercised one drifts, and the
moment it runs is the moment nobody is watching.

**This is why "fail fast exposes real issues faster" is a stronger claim
than it sounds.** It is not mainly about debuggability. A fallback is
code with no users, and code with no users is wrong by the time it runs.

### 6.89 The Demo Page Is the Integration Test You Already Wrote (2026-10-16)

Two pages in this repository had never worked:
`demo/components/spinemap.html` configured a `periodpicker` and a
`richtextinput` and loaded neither bundle, and
`demo/components/formdialog.html` loaded FormDialog without
confirmdialog, so its unsaved-changes prompt had never once fired.

Both looked perfect. The fallbacks drew a text box and closed the dialog,
which is exactly what a casual look expects to see.

Removing the fallback is what surfaced them, and in the same motion
Toolbar's own unit suite turned out never to have loaded Bootstrap — 22
passing tests in which every tooltip silently did nothing.

**A demo page is a consumer, and it is the one consumer whose breakage
you can see for free.** When changing what a component demands, grep the
demos before pushing. The first time, this was luck. The second time it
was a checklist item, and it found a second page.

### 6.90 Normalisation Is Not Substitution, and the Sweep Needs That Line (2026-10-16)

A blanket "remove every fallback" would have deleted correct code. Three
cases branch on which API is available and are right to:

- `getDriverJs` probes `driver.js.driver` and `driver.driver`, two export
  shapes of **one** library.
- MarkdownEditor's `getHTML()` path uses another method of the **same
  live Vditor instance** it already holds.
- DiagramEngine tries `show`, `render` and `getElement` across
  **heterogeneous** embedded components.

The distinguishing question is not "does this code have a second branch".
It is **"is the thing I am reaching for missing, or merely shaped
differently?"** Normalising a shape yields the real result. Substituting
for something missing yields a different result wearing the same name.

Of the eleven items on the provisional list, eight were cleared on this
test and the review added seven that were not on it. **The list produced
by grepping for the word "fallback" was both too long and too short**,
which is the ordinary condition of a list made from a name rather than a
behaviour.

### 6.91 A Deferral List Gets Severity Wrong in Both Directions (2026-10-16)

Three findings were parked as FALLBACK-9: "not fallbacks, need their own
decision". Working them produced three different corrections to the
entry that described them.

- **RibbonBuilder** was estimated at ~150 lines of working UI to delete.
  It was 334, and the picker held 176 hand-listed icons, so the entry
  undersold both the cost and the defect.
- **DiagramEngine** was recorded as one hardcoded string. It was that,
  plus two placeholder fallbacks that made the fix invisible, and the
  hardcoded string had been displaying on every markdownrenderer embed
  ever placed on a diagram.
- **Toolbar** was recorded with the wrong fix. The entry read it as a
  dependency-width problem and prescribed narrowing; the real problem
  was a declared contract nothing enforced, and narrowing would have
  built tolerance for violating it.

**Principle**: a deferral written while the real work is happening
elsewhere is a note about code nobody has touched. Nothing in it has
been run, so its cost estimates, its severity and its prescribed fix are
all guesses made at the moment of lowest information. Re-read the code
before acting on your own deferral, and expect the entry to be wrong.

### 6.92 The Fallback Two Functions Up Swallowed the Refusal (2026-10-16)

The DiagramEngine fix replaced an invented string with a throw. The test
for it failed: no error arrived, nothing rendered. `invokeFactory`
wrapped the entire mount chain in a catch that logged and drew a
placeholder, so the new refusal was caught by a fallback two frames above
it and turned back into a dashed grey box.

**A refusal is only as loud as the quietest catch between it and the
user.** Removing one fallback inside a call tree that still has another
above it does not change behaviour; it moves which fallback answers. The
test is what proved it, because the code change looked complete.

The corollary is about the placeholder itself. A dashed box with an icon
and the component name **looks like a deliberate part of a diagram**, so
a broken embed read as a designed one and nobody went looking. An ugly
stand-in is worse than an empty space, because an empty space provokes a
question.

### 6.93 A Required Field a Type Cannot Enforce Is a Runtime Check (2026-10-16)

`ToolItem.tooltip` has been `tooltip: string` since the file was written,
commented "Required for accessibility". The component trusted the type
and interpolated it straight into `title` and `aria-label`. A host
written in JavaScript — every demo page in this repository — could omit
it, and the button went to the DOM announced as "undefined", with a
Bootstrap trigger attached to show that word on hover.

**Principle**: a published component's types are documentation to half
its callers. Where a field is required *and* its absence produces a
fabricated value rather than a visible gap, the type needs a runtime
companion. The tell is interpolation: `aria-label: item.tooltip` cannot
fail, it can only produce the string "undefined".

Note which direction the fix goes. The tempting fix is to stop setting
the attribute when the value is missing, which is tolerance for a
violated contract — a fallback wearing a narrowing costume.

### 6.94 A Zero Is a Claim About a Predicate, Not About the World (2026-10-17)

DEBT-SEC-6 closed on 2026-10-15 having pinned eleven floating CDN URLs,
and `unpinnedCdnRefs` was reported as "held at 0". On 2026-10-17 the
same check, with its registry list widened from one host to four,
returned **77** — against documents nobody had touched in between.

The predicate matched `cdn.jsdelivr.net` and nothing else. Fourteen
esm.sh specifiers floating at major `@6` and eight unpkg paths carrying
no version at all had been outside it the whole time. The zero was true
of the predicate and false of the repository.

**Principle**: when a check reports zero, the question to ask is not
"is this right" but "what can this check see". A green count names the
intersection of the defect and the predicate, and only the predicate is
written down. This is the third time in this repository. DEBT-GATE-1 was the
first, where `grep -oP` aborted on macOS and three checks passed on
an empty list. DEBT-DUI-5 was the second, where a measurement matched
the wrong CSS property and the wrong unit.

The tell is a zero that arrived without effort. Eleven URLs were fixed
to reach that zero, which made it feel earned. The earning is what
stopped anyone asking what else the pattern missed.

### 6.95 A Ceiling Cannot See a Predicate Narrowing (2026-10-17)

This repository already knows that a ceiling cannot see an absence. The
sharper case is a ceiling watching a count whose *definition* changes.

Reverting the registry widening above takes `unpinnedCdnRefs` from 77 to
0 and `thirdPartyTagsWithoutSri` from 76 to 28. Both are ceilings. Both
report "under baseline". The audit prints PASS, and the only thing that
happened is that the check stopped looking at three registries.

**Principle**: a ratchet guards the number, never the meaning of the
number. Anything load-bearing about *what* is counted belongs in unit
cases, where narrowing the predicate fails a test instead of relaxing a
ceiling. The four registries are therefore pinned in
`scripts/audit-counts.test.ts`, with a pinned and an unpinned case each.
The mutation that narrows the host pattern fails three of those cases
while the audit still passes.

A baseline is a promise about a quantity. A test is a promise about a
definition. Only one of them notices when the definition moves.

### 6.96 An `integrity` Attribute With No `crossorigin` Is Not Protection (2026-10-17)

A `<script src>` on another origin, carrying a correct `integrity` hash
and no `crossorigin` attribute, is fetched as an opaque response. The
browser cannot read the body, so it cannot hash it, so it **skips** the
integrity check rather than failing it. The script runs unverified.

**Principle**: this is the worst shape a security control can take. It
is not absent, which somebody would notice. It is present, correct, and
inert. A reviewer reading the tag sees a hash and stops reading.

So the check that guards this repository's documented tags requires both
attributes and counts a tag carrying only the hash as a failure. The
mutation that drops the `crossorigin` half of the condition fails a case
written for exactly that half.

### 6.97 A Fixture the Code Filters Out Never Reaches the Assertion (2026-10-17)

The first draft of the `countTagsMissingSri` cases used placeholder URLs
— `src="URL"`, `href="S.css"`. The function matches tags on a CDN host
before it reads any hash, so every fixture was discarded before the
logic under test ran. Four cases failed loudly and were fixed.

The fifth did not fail. "A correctly hashed tag costs nothing" expects
zero, and a fixture that is filtered out also returns zero. It would
have passed for the rest of its life while testing nothing.

**Principle**: a case whose expected value is zero, absence or no-op
cannot distinguish "the code did the right thing" from "the code never
saw the input". Give such a case a sibling on the same fixture that
expects a non-zero result. If the sibling passes, the fixture reaches
the code, and only then does the zero mean anything.

This is the same shape as the DiagramEngine suite that stayed green for
months while pointed at a page that loaded nothing.

### 6.98 A Count of Attributes Cannot See a Wrong Attribute (2026-10-17)

`thirdPartyTagsWithoutSri` counts third-party tags carrying no
`integrity` at all. That is the right predicate for coverage, and it is
blind to the failure one step along: a tag that carries an integrity
attribute belonging to a different file.

The mutation was small. Take a fixed DOMPurify tag, swap
`static.knobby.io/lib/dompurify-3.4.16.js` back to
`unpkg.com/dompurify@3.2.4/dist/purify.min.js`, leave the hash where it
is. The count stayed at 65. Nothing in the audit moved, because the tag
still has an `integrity` attribute. The browser would have refused the
script, which is the correct outcome, but no gate in this repository
would have told anyone before a consumer hit it.

**Principle**: a hash is a claim about exactly one URL, so a check on
the presence of the hash measures half of the claim. The other half
needs asserting in the opposite direction — given a published hash,
does the tag carrying it point at the URL that hash came from.
`scripts/check-closure.mjs` now does that, and the gate reports how
many tags it inspected so a PASS states coverage rather than only the
absence of a complaint.

Third of this family after 6.94 and 6.95. A zero was a claim about a
predicate, a ceiling could not see a predicate narrowing, and now a
ceiling cannot see a predicate that was always too weak.

### 6.99 Check What the Manifest Serves Before Believing What the Entry Lists (2026-10-17)

DEBT-SEC-8 described eight libraries each needing its own version or
registry answer. Half the list was wrong, and the error was one lookup
deep. `dist/lib-manifest.json` serves seven assets. ADR-149 recorded
four. Nobody widened the entry when chart.js, vditor and font-awesome
were added, so three libraries this origin already vendors and hashes
were filed as open third-party decisions, next to a fourth, DOMPurify,
that the entry did identify.

The entry said font-awesome was "hashable in one line, cdnjs". The
truth was that `/lib/font-awesome-6.5.1/css/all.min.css` had been
serving all along while a README handed out cdnjs 6.5.0. It said
vditor needed a registry picked. Both registries serve the same 3.11.2
that `/lib/` serves, so the registry was never the question.

**Principle**: an entry describing external state is a snapshot of when
somebody last looked. Before acting on its shape, re-read the artifact
it describes. One `curl` of the manifest reframed four of eight rows
from "needs a decision" to "needs a line of documentation".

Same family as DEBT-SEC-3, where a deferral rested on "`npm audit` is
already 0" and the premise had quietly expired. A deferral justified by
a measurement needs the measurement re-taken, not the conclusion
re-read.

### 6.100 A URL Nobody Fetches Is a URL Nobody Checks (2026-10-17)

`components/latexeditor/README.md` documented MathLive at
`cdn.jsdelivr.net/npm/mathlive@0.107.3/dist/mathlive.min.js`. The fetch
returned 52 bytes: "Couldn't find the requested release version
0.107.3." Version 0.107.3 was never published. The 0.107 line stops at
0.107.1. The real asset is `mathlive.min.js` at the package root, not
under `dist/`.

So the URL is wrong twice over, and it has never worked. It survived
because MathLive is optional, detected with
`customElements.get("math-field")`, and the component drops to source
mode when the element is absent. A capability probe that finds nothing
looks exactly like a consumer who chose not to load the library.

**Principle**: an optional dependency is an untested dependency unless
something fetches its documented URL. The repository had a ceiling
counting whether the tag carried a hash and no check on whether the tag
resolved. Pinning and hashing a URL says nothing about whether it is
real — SEC-6 found `bootstrap@5/css/bootstrap.min.css` returning 404 in
the same way, and this is the second instance.

### 6.101 What a Hash Covers Is Narrower Than the Library (2026-10-17)

Four of the eight assets hashed this week pull something at run time
that the hash does not reach. KaTeX's stylesheet names 60 `@font-face`
files. Font Awesome is a stylesheet plus webfonts. MathLive reads
`fontsDirectory` relative to its own script URL. vditor injects its
markdown engine, icon set, language pack and every optional renderer as
script tags it writes itself, defaulting to a hardcoded unpkg URL.

Only three of the eight are honestly `"closure": "complete"`.

**Principle**: record what the hash covers in the same field that
records the hash, in the artifact rather than in prose somewhere else.
`scripts/third-party-sri.json` has a `closure` key for exactly this, and
the useful entries are the ones that are not the word "complete". An
`integrity` attribute invites the reader to believe the library is
verified. What is verified is one file.

vditor is the sharpest case, because the gap is not a font. A
substituted font renders wrong glyphs. A substituted markdown engine
runs.

### 6.102 An Override Written to Close a Hole Can Open a Different One (2026-10-17)

`MarkdownEditor` sets vditor's `cdn` option so the lazily-injected
chunks never reach unpkg, and the constant's own comment says so:
"Never fall through to a public CDN: that is the behaviour this
constant exists to remove." It is the right call and it is working.

It resolves the origin from `document.currentScript.src`. So a consumer
who self-hosts `markdowneditor.js` makes vditor look for
`/lib/vditor-3.11.2/` on their own origin, which they will not have
unless they mirrored it. The component refuses to paper over that, which
is the no-fallback rule doing its job, and the README said nothing about
it until now.

**Principle**: an override that derives its target from the environment
has moved the requirement rather than removed it. Write down where the
requirement landed. The fix here was a paragraph, not code, and it was
only visible because repointing the entry tag forced someone to ask
where the rest of the library comes from.

### 6.103 To Measure What Code Does, Run It (2026-10-17)

ERR-1 asked how many factories validate their container. The first
attempt read each factory body and reported 2 of 46. Calling them
reported 9 of 74. The static read was wrong in both directions at once,
and the reason is structural rather than a bug in the regex.

The factories are thin. `createDatePicker` forwards to a constructor.
`createColorPicker` forwards to `show()`. The decision to warn rather
than throw is taken two hops from the text being read, so a reader of
the factory body is measuring the wrapper.

**Principle**: when the property under measurement is behaviour, the
instrument is a call, not a pattern. The census imports each component,
calls each factory with a container that exists and then with one that
does not, and records what happened. The ceiling lives in a test file
because `scripts/audit-counts.mjs` has no DOM, and that is the right
trade: a ratchet that measures the wrong thing cheaply is worse than one
that measures the right thing in a test.

The control call matters as much as the real one. A component that
refuses a missing dependency throws on both calls and never reaches the
container, so counting it as validating would be the vacuous green this
repository keeps finding.

### 6.104 A Sweep Finds the Shapes It Was Written to Match (2026-10-17)

FALLBACK-1 through 9 reviewed every fallback in the fleet, and the
review was thorough. It keyed on `catch`, on a method literally named
`fallback()`, and on `??`.

`colorpicker.show()` is this:

```ts
if (!container)
{
    logWarn("Container not found:", containerId);
    return;
}
```

A loud failure converted to a quiet wrong answer, which is the owner's
definition exactly. It matches none of the three keys. Fifty-one
factories do this and fourteen more do it with no log at all, and the
nine-part sweep walked past all sixty-five.

**Principle**: a sweep's coverage is the union of its patterns, never
the concept it was named after. State the patterns in the record, so the
next reader knows what was not looked at rather than inferring from the
title that everything was. "Reviewed all fallbacks" and "reviewed every
`catch`, `fallback()` and `??`" are different claims, and only the
second one was true.

ERR-1 and the fallback review turn out to be the same work. Neither
entry says so.
