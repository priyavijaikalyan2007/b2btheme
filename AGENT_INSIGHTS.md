# Agent Insights

Insights are hard-won lessons from real bugs, user feedback, and architectural decisions. Each insight captures a *principle* — not just what happened, but *why* it matters and *how* to apply it going forward.

**For agents**: Read this file at session start. When you discover a new insight during implementation, append it to the appropriate section with the date and a concise description. If no section fits, add a new one.

---

## 1. Cross-Repo & Cross-Team Contracts

### 1.1 Verify the Other Repo Before Planning "Their" Work (2026-07-11)
The Keycloak parity spec assigned R1 (theme-cookie write) to the apps team as outstanding work. Reading the apps repo directly (`~/work/knobby/apps`) showed `theme-manager.ts` had **already shipped** the cookie exactly per the R3 contract, and `apps/specs/infra/keycloak.prd.md` already documented the URL this repo was expected to publish. The plan changed from "draft an R1 patch" to "verify and hand off" — and revealed the theme repo was the actual blocker.

**Principle**: When a spec splits work across repos you can read, ground every "owned by the other team" claim in their code before planning. Specs go stale the moment either side ships.

### 1.2 Frozen Contracts Need an Executable Drift Guard (2026-07-11)
The AuthCard class structure is mirrored verbatim by Keycloak FreeMarker templates that live in another repo and deploy on a different cadence. Documentation alone cannot stop a well-meaning rename from silently breaking the mirror. The "canonical structure" test block in `authcard.test.ts` turns the contract into CI: any class/structure change fails the build here, before it breaks the login page there.

**Principle**: When markup or class names are consumed verbatim by an external system, encode the frozen surface as structure-assertion tests in the producing repo. A contract without a failing test is a hope.

### 1.3 Acceptance Criteria Can Exceed the Requirement Text (2026-07-11)
Spec R2 described theme-init as a synchronous pre-paint *set*, but acceptance criterion #3 ("toggling OS appearance while on the page updates it") silently requires a live `matchMedia` change listener. Implementing only the R-text would have passed review and failed acceptance.

**Principle**: Derive the implementation checklist from the acceptance criteria, not the requirement prose — and flag mismatches back to the spec owner so the text gets fixed.

## 2. CDN & Consumption Model

### 2.1 Pinning and No-Redeploy Are Opposing Goals — Pick Explicitly (2026-07-11)
Hard version pinning (or SRI hashes) maximizes tamper resistance but forces every consumer redeploy on every CDN release; SRI additionally bricks pages on any byte change. For same-organisation origins where the trust boundary is the Cloudflare account anyway, "latest + additive-only contract + CI drift guards" preserves evolution without redeploys (ADR-139, `CDN_CONTRACT.md`).

**Principle**: Choose a consumption model by asking *who must redeploy when this asset changes* and *what actually anchors trust*. Write the decision down; do not leave pinning policy implicit.

### 2.2 Cloudflare `_headers` Rules Accumulate — Keep Patterns Disjoint (2026-07-11)
Cloudflare static-asset `_headers` applies **every** matching rule, so overlapping patterns (`/icons/*` and `/icons/fonts/*`) emit duplicate `Cache-Control` headers with conflicting values.

**Principle**: Author `_headers` with mutually exclusive path patterns; comment the constraint in the file itself so the next rule addition doesn't reintroduce overlap.

## 3. Build Pipeline

### 3.1 Non-UI Scripts Can Ride the Component Pipeline (2026-07-11)
`theme-init.js` is not a UI component (no factory, no CSS, no stencil), but placing its source under `components/themeinit/` reused the entire tsc → export-strip → IIFE-wrap → terser pipeline and co-located vitest discovery (`components/**/*.test.ts`) for free; a one-line `cp` in `copy:js` published the canonical `/js/theme-init.js` URL. The exemption from UI-component conventions is documented in ADR-137.

**Principle**: Before building new pipeline machinery for an odd artifact, check whether the existing conveyor can carry it with a documented exemption. One copy step beats a parallel build path.

### 3.2 Generated Files Bite Manual Editors (2026-07-11)
`COMPONENT_INDEX.md` is regenerated by `npm run build` — hand edits are silently overwritten. Its description extractor also read the *continuation lines* of multi-line SPDX comment blocks in READMEs, leaking license text into descriptions (visible on `explorerpicker` long before this session).

**Principle**: Check a file's header for a generated-file banner before editing. When generated output looks wrong, fix the generator — the same defect is usually visible in older entries, and fixing it heals them all.

### 3.3 Count Assertions Are Change Detectors, Not Bugs (2026-07-11)
Adding the AuthCard stencil failed four diagramengine tests asserting exact shape-pack counts (111/138/150). That is those tests working as designed — forcing every stencil addition to be acknowledged.

**Principle**: When a count assertion fails after an intentional addition, update the expected count in the same commit as the addition, and say so in the commit message. Never widen the assertion to "greater than".

## 4. Security in a Component Library

### 4.1 Trusted-Markup Inputs Deserve a Named Boundary (2026-07-11)
AuthCard renders every option string via `textContent` — except provider icons, which are inherently markup (inline brand SVGs). Rather than accepting arbitrary HTML, the `iconSvg` option is (a) documented as app-authored-literals-only, (b) parsed with `DOMParser` and discarded unless the result is a single well-formed `<svg>` root, and (c) tested with an injection payload.

**Principle**: When a component must accept markup, isolate it to one named option, validate its shape as defense-in-depth, and state the trust requirement in the README — "trusted" is a documented contract, not an assumption.

## 5. Library Boundaries

### 5.1 "The App Shouldn't Have To Do Extra Work" Beats a Clean-Sounding Boundary (2026-08-09)
`spot` anchoring shipped with the *field* but not the *gesture*: the model could express "mark this place", but nothing turned a click into one. The rationale — the repo ships capability, applications ship behaviour — sounded principled and was recorded as Accepted in an ADR. The owner rejected it: recording where a click landed is coordinate translation, and every consuming app would re-derive the same zoom, scroll and pan arithmetic to do it. Persisting the resulting document is the app's job; producing it is not.

**Principle**: The boundary test is not "is this behaviour or capability?" — it is "would every consumer write the same code?" If they would, and it needs knowledge only the library has (its own transforms, its own DOM), it belongs in the library. State a boundary as a *proposal* until the owner rules; do not write it into a durable record first.

### 5.2 Capture and Restore Must Live Adjacent, With a Round-Trip Test (2026-08-09)
Click-to-place needs forward math (pointer → recorded fraction) and inverse math (fraction → screen position). They are asymmetric: capture starts from `getBoundingClientRect`, which is measured *after* the canvas's `scale(zoom)`, and must divide zoom out before mixing in `scrollLeft`, which is not scaled; restore works entirely in layout pixels. Housed in separate sections they drift, and a drifted pair does not throw — it puts the mark somewhere plausible.

**Principle**: Write inverse functions next to each other, say in a comment that they are inverses, and assert the identity end to end (place → reload from the persisted log → same position). A test of only one direction cannot see drift.

### 5.3 A Fraction Is Meaningless Without Naming Its Box (2026-08-09)
"A fraction of the target" is ambiguous the moment a mounted component scrolls internally. A note longer than its card scrolls its own textarea; a grid scrolls its own rows; a plain document lets the frame body take the overflow. Anchoring everything to the body leaves marks behind on internal scroll — silently, since nothing errors.

**Principle**: When recording a relative position, record *what it is relative to* as part of the anchor. Also: `scroll` does not bubble, but capture-phase listeners on an ancestor still receive it, so one listener on the root tracks every scrolling region — including ones a component creates long after mount.

### 5.4 An Untestable Branch Is an Unshippable Branch (2026-08-09)
The scrolling-region machinery had zero coverage: every test took the index-0 path because nothing on the demo page scrolled internally. The cause was mundane — the demo loaded `datagrid.js` but not `datagrid.css`, so the grid's scroll container had no `overflow` rule. The branch looked exercised because tests near it passed.

**Principle**: When a branch exists for a case, prove the case occurs before believing the tests cover it. Print the discriminator (here, the recorded index) in a probe rather than inferring coverage from green.

### 5.5 Measure the Page, Not Just the Widget, When a Position Looks Wrong (2026-08-09)
A placement test failed by 18px and the geometry was blamed twice. The actual cause: the demo wrote its result into the five-line instruction paragraph, collapsing it to one line, which reflowed the page and moved the canvas 17px between the click and the measurement.

**Principle**: When measured positions are off by a constant, probe the containers as well as the element — including whether your own status output changed the layout. Reserve height for anything that updates in place.

### 5.6 Overlay Exemptions Must Cover Obstacles, Not Just Occupancy (2026-08-09)
The packer skipped overlays when *placing* nodes but still added a fixed-placement overlay to the *obstacle* list, so a mark dropped on bare canvas pushed nearby nodes aside — the exact displacement overlays exist to prevent. A second bug in the same function ignored `placement` entirely for unanchored overlays and marched them along the top of the region, discarding the coordinates they were given.

**Principle**: A layout exemption has two halves — "does not get placed by the packer" and "is not treated as an obstacle by it". Assert both: compare a node's rectangle with and without the overlay present.

### 5.7 A Test Suite That Cannot Reach Its Subject Fails Loudly and Means Nothing (2026-08-10)
67 DiagramEngine e2e tests failed on `createDiagramEngine not found on window`. The engine was fine; the spec navigated to the component *gallery index*, which links to every component page and loads none of them. The failure looked like 67 broken features and was one broken URL. Repointing fixed all 67 with no engine change.

**Principle**: When a whole suite fails identically, suspect the harness before the subject — and check what the page under test actually loads. Then prove the repaired suite is not vacuous by mutating the implementation and watching it fail. Mutate the *exact* line the assertion depends on: a first attempt here changed two unrelated `shape:"rectangle"` literals, nothing failed, and that reads precisely like a toothless suite.

## 6. Public-Surface Components

### 6.1 A "No JavaScript" Request Can Still Need a Factory (2026-09-01)
The website asked for CSS-first components requiring no JavaScript, and the honest reading was two folders containing only SCSS. That reading was wrong for a structural reason, not a stylistic one: `runtime/fleet-conformance.test.ts` enumerates every directory in `components/`, and `demo/studio/component-studio.html` registers each entry by a **factory name string**. A component with no factory cannot appear in Component Studio at all and needs a `NOT_MOUNTABLE` entry in a category reserved for services and overlays. AuthCard had already settled the same tension from the other side — "the CSS is the contract; the JS is a convenience" — because Keycloak's templates link only the stylesheet.

**Principle**: Before honouring a constraint literally, find what in the repository is *keyed* to the thing you are about to omit. The factory here is not overhead paid for the consumer that never calls it; it is what buys the stencil, the studio entry, and the conformance gate.

### 6.2 Two Acceptance Criteria Can Contradict Each Other (2026-09-01)
The hero request asked for an eyebrow above the heading *and* for "the heading remains the first item in document order". Both are reasonable; together they are unsatisfiable in plain source order. Silently dropping either would have shipped something the requester believed they had. Resolved by naming the conflict, choosing `order: -1` on the eyebrow, and stating why it is safe — nothing in that block is focusable, so displaced visual order carries no keyboard hazard, whereas nesting the eyebrow inside the `h1` would pollute its accessible name.

**Principle**: When two requirements collide, surface the collision and propose a mechanism, rather than picking one and hoping the omission is not noticed. The mechanism is what the requester actually needs to approve.

### 6.3 A Pipe Swallows the Exit Code You Were Checking (2026-09-01)
`npm test 2>&1 | tail -40` was reported as exit code 0 while the output plainly read `sh: tsc: command not found`. The zero belonged to `tail`. `node_modules` was not installed and the suite had not run at all — one step from announcing a green tree on the strength of a truncated log.

**Principle**: Never take the exit status of a pipeline as the status of the command that matters. Use `set -o pipefail`, capture to a file and check separately, or read the tail before believing the code. A suite that did not run looks identical to a suite that passed if you only check the number.

### 6.4 "Pre-existing" Is a Claim You Must Prove, Not Assert (2026-09-02)
137 tests failed mid-task and were reported as pre-existing. The user pushed back — *"these tests used to work fine before you edited the code so they cant be preexisting"* — and was right to. Stashing the work and re-running was suggestive; what actually ended the argument was a clean worktree checked out at the session-start commit, with the new files provably absent, failing identically 64/64, followed by the same tree passing 64/64 with one Node flag added. The first experiment isolates the code, the second names the cause.

**Principle**: When you believe a failure is not yours, do not say so — demonstrate it with a tree that cannot contain your work, then flip the suspected cause and watch the result change. And drop the phrase itself: "pre-existing" reads as *not my problem* even when accurate. The user's belief was also correct in its own terms — the tests had passed, on an older interpreter.

### 6.5 Never `git add -A` in Someone Else's Working Tree (2026-09-02)
The close-out commit used `git add -A` and swept up `LANGUAGE.md`, a file the user had left uncommitted and that had been deliberately excluded three times over the session. It cost a `reset --soft`, an unstage, and a rewritten commit — cheap only because it was caught before the push.

**Principle**: In a tree carrying work that is not yours, stage by explicit path. `git add -A` is a statement that every modification in the tree belongs to your change, which is false the moment a collaborator has anything in flight. Read `git status` before committing, not after.

### 6.6 When a Whole Suite Breaks, Suspect the Interpreter (2026-09-02)
Node v26 broke this repository twice in one session, in unrelated places. It ships an experimental `localStorage` global that shadows jsdom's and is undefined without `--localstorage-file`, taking out 137 storage-using tests; and Playwright's Chromium download hangs under it, leaving the e2e suite unable to launch a browser at all. Neither is a repository defect and neither appears in any changelog the repository owns.

**Principle**: A suite that passed last month and fails wholesale today, with one error shape repeated across unrelated files, is an environment change until proven otherwise. Check `node --version` early. Runtimes now ship browser globals that silently shadow the ones your test environment installs, and shadowing produces `undefined`, not a clean `ReferenceError`.

### 6.7 A Demo Page Nobody Can Navigate To Is Half-Delivered (2026-09-02)
Both new components shipped with working demo pages, correct asset paths, and 200 responses — and neither appeared in the gallery, because nothing linked to them. `demo/index.html` is the only page that indexes component demos, and the plan's tasks said "create the demo page" without saying "register it". The deliverables checklist inherited the same gap, so every box was ticked while the pages stayed unreachable. The user found it by looking at the index, which is the one check no automated test performed.

**Principle**: For any artifact that lives in a catalogue — a demo page, a stencil, a studio entry, a manifest — the deliverable is *creation plus registration*. Ask "what links to this?" and verify the link from the entry point a human would actually use. A file that exists and a file that is reachable are different claims, and only the second is what "shipped" means.

### 6.8 A Colour Change Is Not Verified Until the Ratios Are Computed (2026-09-08)
The visual-refresh spec stated, from reasoning about which direction each surface moved, that "no ratio is reduced by D2". It sounded right: the lightest surface got lighter, the darkest got darker, text colours did not move. Measuring every text-on-surface pair in a browser found **two** AA failures, both introduced by the change. Muted text on the new darker page ground fell to 3.94:1 — and the measurement also revealed it had been sitting at 4.54:1 beforehand, marginal and unexamined for as long as the token had existed. The second failure came from a decision made *in the same spec*: tinting the active tab label with `--theme-primary`, a colour tuned to be legible as a fill, measured 3.91:1 as type on chrome.

**Principle**: Contrast is arithmetic, not judgement, so never assert it in prose. Compute every text-on-surface pair against the built stylesheet and paste the numbers into the spec. Two corollaries worth keeping: a colour that passes today may be passing by hundredths, so moving *any* background re-opens every ratio that lands on it; and a colour approved as a **fill** is a different decision from the same colour as **type** — if a design tints a label with an accent, that pairing needs its own measurement and usually its own token.

### 6.9 Ask Which Variable the Rule Actually Drives Before Bumping It (2026-09-08)
"A bit more spacing" reads like a one-line change: raise `$spacer`. In this repository that would have been wrong. `$spacer` drives only Bootstrap-level padding; the `$sp-*` fixed-pixel scale used throughout component internals and the `$control-height-*` tokens are independent of it. A global bump would have grown some components and left others exactly as they were — a result less coherent than the starting point, and one that looks like sloppiness rather than a decision.

**Principle**: Before turning a global knob, enumerate what actually reads it. A token that governs 30% of the surface area produces uneven results when moved wholesale, and unevenness is more visible than the tightness it was meant to fix. Prefer a small number of named, targeted values you can defend individually over one global that moves things you did not inspect.

### 6.10 Sweeping by the Old Value Misses Defaults-by-Omission (2026-09-09)
Adopting a new radius token took three rounds, and each round's sweep was defeated by a different kind of invisibility. Round one changed the tokens and assumed consumption. Round two swept every component that set `border-radius: 0` — 51 sites — and still left the interface looking largely unchanged. Round three found the actual majority: **71 of 125 components never declared a radius at all.** They rendered square not because they opted out but because they never opted in, and absence of a declaration is invisible to grep. The same round found `dynamiccanvas.scss` consuming `var(--theme-border, …)` and `var(--theme-surface, …)` — two token names that do not exist — and silently using its hardcoded fallbacks in both themes since the file was written, because a CSS custom-property fallback fails quietly by design.

**Principle**: Auditing token *adoption* is not the same as auditing token *values*. Ask "which components never reference this token at all", not "which components set it to the old value" — the second question only finds the ones that already knew the token existed. Two corollaries: a CSS custom-property fallback is an error that never reports itself, so periodically assert that every `var(--x, fallback)` names a token that is actually defined; and when a change lands with less effect than expected, suspect unreached consumers before reaching for a bigger value.

### 6.11 On a Dark Ground, a Black Shadow Is Not a Weak Signal — It Is No Signal (2026-09-09)
Dark mode shipped with no visible elevation, and the instinct was to raise the alpha. The arithmetic says that could never have worked. Against a `#0d1420` page, a black shadow reaches 1.034 contrast at alpha 0.22 and only 1.106 at 0.75 — while a light-mode shadow at alpha 0.08 already reaches 1.192. The ground is near-black, so a darker shadow has nowhere to go; the returns are not diminishing, they are nearly absent. What reads as "lifted" on a dark ground is a hairline **light** ring at the element's edge, plus the surface tint the elevation ladder already provides.

**Principle**: Elevation in dark mode is a different mechanism, not the same mechanism turned up. Compute the contrast between shadow and ground before tuning opacity — if the ground is within a few percent of black, reach for a light edge instead. The same physics explains why directional edge shadows on docked dark chrome need to become lit seams rather than dark ones.

### 6.12 A Data File Nothing Parses Will Quietly Stop Being Data (2026-09-09)
`agentknowledge/history.jsonl` had been invalid JSONL since February. Three lines failed `json.loads` — two because an append omitted its trailing newline and put a second object on the same line, one because `\!`, bash history-expansion escaping, leaked through a double-quoted shell append as an invalid JSON escape. Six months passed without anyone noticing, for the simple reason that **nothing ever parsed the file**. It was written by agents and read by humans, and humans read past a missing newline without blinking. Both causes reduce to the same mistake: writing JSON with text tools instead of a serializer, where framing and escaping are your problem rather than the library's.

**Principle**: A machine-readable file needs a machine that reads it, or it degrades into prose that merely looks structured. When you introduce a data file for agents, add the parse to the test suite in the same change — and mutation-test that guard, because a check that only ever runs against a good file proves nothing. The corollary for writing: never assemble JSON, YAML or CSV in a shell string; a serializer exists precisely so that trailing newlines and escape sequences are not judgement calls.

### 6.13 An Override With a Floor and No Ceiling Is a Time Bomb (2026-09-11)
`package.json` carried `"overrides": { "undici": ">=7.24.1" }`, added to force a security patch into a transitive dependency. It worked, and kept working, until undici 8 shipped — at which point the unbounded range resolved to a major version that jsdom@29 does not support. jsdom's dispatcher could not load, every one of the 142 test files failed to start, and vitest reported **"no tests"**: not a failure listing, just an empty project. The suite had gone from 4825 assertions to zero, and the console said almost nothing about it.

**Principle**: A security override expresses two constraints, not one — the floor you are patching *to* and the ceiling the consuming package can actually tolerate. Write `^x.y.z`, not `>=x.y.z`, and record beside it which package's compatibility sets the ceiling, or someone will later widen it back. The second lesson is about reading test output: **"no tests" is a failure mode, not a clean slate.** After any change to the toolchain, check that the suite still *collects* the expected number of files before taking "passing" as meaningful — the same vacuous-suite trap as insight 3.3 and the DiagramEngine harness, arriving by a different route.

### 6.14 Fix the Aggregation Point, or the Leaf Fixes Are Decorative (2026-10-04)
A bug report named four pickers that fabricated a setting after failing to mount. Fixing those four would have changed nothing observable, because `DynamicFormSwitcher` — the generic form host every value-bearing component is driven through — caught adapter throws and returned `undefined`, and invented a typed default for any field that never mounted. Both fed `getValues()`, which is what a host passes to `api.save()`. A picker rewritten to throw would have had that throw converted straight back into a fabrication, one level up and harder to see. The report could not have known: it was written from the outside, where only the leaves are visible.

**Principle**: When a defect has a shape, trace the shape to where values are *aggregated*, not just where they *originate*. The aggregation point is where a host actually reads, so it is where the damage is done — and it is systematically under-reported, because an external reporter sees the component that misbehaved, not the funnel that laundered it. Ask: between this defect and the database, what else touches the value?

### 6.15 A Passing Test Can Be What Holds a Bug in Place (2026-10-04)
`columnspicker` and `spacingpicker` each had a test asserting `getValue().name` equalled a fabricated preset after a *failed* mount. Those tests passed, had always passed, and were pinning a data-loss defect in place: any attempt to make the factory refuse would have broken them, and the obvious reading of a red test is "my change is wrong". The reporting team had hit exactly this on their side and warned us about it — while explicitly saying "yours is not that". It was. Separately, `layoutpicker` had no test file at all, which is why its defect went unnoticed by the reporters, the suite, and three prior sessions.

**Principle**: Read what a test *requires*, not just whether it passes. A test that pins a failure path to a specific returned value has encoded that the failure path should produce a value — which is the defect, stated as a requirement. When fixing a behaviour, grep the suite for assertions about the old behaviour *first*, and treat each as a question ("was this ever right?") rather than as a constraint. And absence of a test file is not neutral: it is where defects accumulate undisturbed.

### 6.16 An Incomplete Instruction Licenses the Defect as Surely as a Wrong One (2026-10-04)
The apps team attributed this pattern to two instructions contradicting each other, and asked us to check for our copy. We had neither. What we had was `FRONTEND.md:87` — *"if a component cannot initialise, log the error and leave the DOM unchanged"* — which is not wrong. It mandates exactly the two things the defective code already did correctly, and is silent on the third: do not answer. An agent following that line precisely writes `createNullPicker()` and has obeyed every word.

**Principle**: When a rule keeps getting broken, check whether it is being *disobeyed* or *completed*. An instruction that enumerates some obligations implies the list is exhaustive, so the gap reads as permission. Fixing it means adding the missing clause, not restating the existing ones more firmly — and the sharpest test of a safety rule is to ask what the most literal-minded compliant reading produces.

### 6.17 Vendoring a Dependency Makes You Its Maintainer — Which Is the Point (2026-10-04)
The request was to re-serve DOMPurify from our own origin so the apps stopped trusting a public CDN, and the report put it first with a good argument: every other asset degrades when substituted, while a substituted sanitizer *becomes* the attack. Pinning the version the apps use — 3.2.4 — in order to vendor it put it under our `npm audit` for the first time, which immediately reported **nineteen open advisories against it, including XSS bypasses**. The asset we were being asked to protect from substitution did not need substituting. Moving the host would have changed nothing about the actual exposure, and would have lent our origin's legitimacy to a vulnerable sanitizer.

**Principle**: Taking an asset onto your infrastructure means taking on its patch duty, and the first exercise of that duty is often the most valuable thing the migration produces. Pin the dependency properly (lockfile, audit coverage) *before* designing the serving layer — the audit result may reorder the work, or reveal that provenance was never the binding problem. More generally: when asked to secure the delivery of something, check the thing as well as the channel.

### 6.18 Assert the Property, Do Not Grep for It (2026-10-04)
"This artifact is self-contained" needed to be true, because SRI cannot attach to a runtime import — an artifact that fetches one more module leaves the whole hole open, one level down. The first check was a regex for `import(` over the minified bundle. It reported three violations in maxGraph, every one a false positive: a class method named `import`, matched three ways as the pattern was tightened. The real answer came from esbuild's `--metafile`, which lists every input and marks any unresolved specifier as external — 240 inputs, zero externals, stated by the tool that did the bundling.

**Principle**: When a build tool already computes the property you want to assert, ask it rather than inspecting its output. A regex over generated code tests your model of the output format; the tool's own metadata tests the thing itself. The tell that you are on the wrong side of this line is tightening a pattern to silence false positives — each tightening is a guess about syntax, and the next guess is the one that hides a real violation.

### 6.19 Measure the Adjacencies That Occur, Not the Matrix (2026-10-06)
Tuning the surface ladder, the obvious move was to maximise contrast between all four planes. Doing that fought itself: pushing `sunken` darker to separate it from `ground` cost muted-text contrast everywhere, and the pair being optimised — a well against the page ground — **never appears on screen**. Wells sit inside content; the page ground is behind chrome. The three pairs that actually abut are `chrome|content` (a sidebar meeting the document), `chrome|ground` (a toolbar over the page) and `sunken|content` (a well inside a card). Optimising for those, and deliberately accepting 1.040 on `sunken|ground`, produced better numbers everywhere that a user can see.

**Principle**: A design token set is a graph of what sits next to what, not a matrix of every combination. Before tuning for contrast, enumerate the pairs that physically touch in the rendered interface and optimise only those — an N×N sweep spends real quality on combinations nobody will ever look at, and the cost lands on the pairs that matter. The same reasoning applies to type scales, spacing ramps and elevation: ask what abuts what.

### 6.20 "Make X More Distinct" Can Be a Geometry Problem, Not a Value Problem (2026-10-06)
The request was to tint chrome so panels stood out. Tinting chrome was tried first and made things *worse*: chrome moved down in luminance into the step below it, and `chrome|ground` collapsed from 1.055 to 1.013 — fixing one boundary by destroying its neighbour. The ladder had four steps packed into a narrow luminance band and simply had no room. The fix was to widen every step, which meant changing values the request never mentioned.

**Principle**: When one element in an ordered scale needs more separation, check whether the scale has room before changing that element. A constrained scale redistributes the problem rather than solving it, and the symptom moves somewhere nobody is looking. Say so explicitly when a local request forces a global change — the reviewer asked for one thing and is about to see everything move, and that is a surprise worth pre-empting rather than discovering in review.

### 6.21 A Gate Earns Its Keep on the Run You Write It (2026-10-07)
The contrast gate was built to prevent *future* regressions — three had already shipped and been caught by hand, and the point was to stop a fourth. On its first execution against an interface that had just been reviewed, measured and accepted, it reported a pair nobody had looked at: `--theme-primary-text` on `sunken` at 4.65, the tightest light-mode pair in the theme. The manual audits that preceded it had measured that token against chrome and content only, because those were the surfaces the design was *thinking about*.

**Principle**: Automation's first value is not catching the next regression, it is enumerating the cases a human audit scoped out. A hand check covers the combinations you have in mind; a loop covers the ones you do not, which is precisely where the unexamined ones live. Write the check even when you believe the current state is clean — if it finds nothing, you have learned your coverage was real, and that is worth the hour too.

### 6.22 Build the Checker Wrong First, Then You Learn What It Must Read (2026-10-07)
The contrast gate failed on its first two runs for reasons that had nothing to do with contrast. It parsed the *first* `:root` block in the compiled stylesheet — which is Bootstrap's, not ours; three exist. Earlier, the browser-side audit for the same values returned `null` for two pairs because the browser serialises white as `#fff` and the hex parser assumed six digits. Both were defects in the measuring instrument reporting cleanly on the thing being measured.

**Principle**: A checker is code and can be wrong, and its failure mode is usually a *false pass* rather than a crash — a `null` that compares as fine, an empty match set that iterates zero times, a block that parses but is the wrong block. So always prove a new check fails before trusting that it passes: mutate the input to break each rule it claims to enforce, one at a time. "It printed PASS" and "it is checking anything" are different claims, and only mutation separates them.

### 6.23 A Translucent Token Hides Its Own Contrast (2026-10-07)
The contrast gate passed cleanly, and eight pairs were still below AA. The reason is that `--theme-hover-bg` is `rgba(15,23,42,.045)` — it has no contrast *of its own*, because what a user sees is the composite of that layer over whatever surface is beneath it. No token names that colour, so nothing in a token-by-token audit can examine it. The worst case was a toolbar button whose own label dropped to 3.69 the moment it was hovered, which had been shipping for a month under two separate contrast reviews.

**Principle**: Any token whose value carries alpha is a *relationship*, not a colour, and a checker enumerating tokens will skip it silently. Enumerate the composites: for each translucent layer, for each surface it could sit on, compute the painted colour and check text against that. A related trap in the same work — when a layer could not be parsed, the first implementation skipped it and reported PASS. For a safety check, unparseable input must fail; a skipped case and a passing case are indistinguishable in the output, and the quiet one is always the wrong default.

### 6.24 Cost the Fix Before Accepting Its Price (2026-10-07)
Reaching zero composited failures appeared to need three changes: darker text, softer state layers, and a deeper accent. That package was presented with its costs, and the softer layers were accepted as the price of strictness. Measuring that specific consequence *before* applying it showed light hover on chrome would fall to **1.072** — against the 1.056 that had prompted the original "not well differentiated" complaint. It would have traded an AA failure for an invisible hover affordance. Re-solving with the layers held fixed showed the text changes alone clear all 96 pairs; the softening was never required.

**Principle**: When a fix bundles several changes, measure each one's cost separately before applying the bundle — and re-solve with the expensive element held fixed. An approved tradeoff is not a mandate to make it: if the price turns out to be avoidable, avoiding it is what was actually wanted. State that you are doing so, since the decision was explicit and the person is entitled to know their constraint was relaxed rather than overridden.

### 6.25 An Inline Background Is a Theme Opt-Out (2026-10-07)
Two dark-mode bugs reported together turned out to be one shape: a background applied as a *fixed value* while the text colour came from the theme. `tr.style.backgroundColor = "#f8f9fa"` and `el.style.background = "#f8f9fa"` both paint the same pixel regardless of `data-bs-theme`, so when the theme flips the text to near-white the content vanishes against its own row. Neither component was using tokens wrongly — one never reached CSS at all, because the factory wrote the colour onto the element.

**Principle**: Writing a colour through `element.style` removes it from the theme, permanently and silently. If a value must come from data — a preset, a user choice, a brand colour — hand it to CSS as a **custom property** and let the stylesheet decide per theme; that keeps the switch declarative and repaints without a re-render. And a background and its foreground are a *pair*: setting one without the other means the unset half still follows the theme and will invert out from under you. Demo code is worth holding to this too, since it is the first thing a consumer copies.

### 6.26 A Documented Limitation Still Reads as a Bug (2026-10-07)
The VisualTableEditor demo stated plainly that "the minimal and striped presets adapt to dark mode automatically" — an accurate description that four other presets do *not*. The behaviour was known, described, and shipped. It was still reported as a defect the first time someone looked at the gallery in dark mode, because what they saw was rows of invisible text, and no prose next to a broken thing makes it look intended.

**Principle**: Documenting a limitation records the decision; it does not discharge it. If the limitation produces output a user would report as broken — unreadable text, a missing control, a silent failure — the document is a note to yourself, not a mitigation. Use the test: would someone encountering this cold file a bug? If yes, the honest options are fix it or make the degraded state legibly deliberate, not describe it in a paragraph they will not read first.
